    Module 1

    Les principes de l'Infrastructure as Code

    L'Infrastructure as Code (IaC) consiste à décrire l'infrastructure (réseaux, machines virtuelles, bases de données, DNS, droits d'accès…) dans des fichiers texte versionnés, puis à laisser un outil créer et maintenir cette infrastructure à partir de ces fichiers. On remplace ainsi les clics dans une console (le « ClickOps ») et les scripts manuels.

    Pourquoi l'IaC ?

    🔁 Reproductibilité

    Le même code produit la même infrastructure, en dev, en recette et en production.

    📜 Traçabilité

    Chaque changement passe par Git : qui, quoi, quand, pourquoi. On peut revenir en arrière.

    👀 Revue

    Les changements d'infrastructure sont relus en merge request, comme du code applicatif.

    ⚡ Rapidité

    Un environnement complet se crée en minutes au lieu de jours, et se détruit aussi vite.

    Déclaratif ou impératif

    Impératif (le « comment »)Déclaratif (le « quoi »)
    On décrit les étapes à exécuter : « crée 3 serveurs », « ajoute 1 serveur ».On décrit l'état final souhaité : « il doit y avoir 4 serveurs ».
    Le résultat dépend de l'état de départ.L'outil calcule lui-même les actions pour atteindre l'état souhaité.
    Exemples : scripts shell, appels d'API, SDK.Exemples : Terraform, CloudFormation, Kubernetes (manifestes YAML).

    Idempotence

    Une opération est idempotente si on peut l'exécuter plusieurs fois sans changer le résultat au-delà de la première exécution. Appliquer deux fois de suite la même configuration Terraform ne crée rien de plus la seconde fois : Terraform constate que l'état réel correspond déjà à l'état voulu et annonce « No changes ».

    Infrastructure mutable ou immuable

    • Mutable : on modifie les serveurs existants (mises à jour, changements de configuration). Avec le temps, les serveurs divergent les uns des autres (configuration drift), ce qui donne des « serveurs flocons de neige » impossibles à reproduire.
    • Immuable : on ne modifie pas un serveur, on le remplace par un nouveau construit à partir d'une image à jour. C'est plus prévisible et plus simple à reproduire.

    Provisioning et gestion de configuration

    On distingue deux familles d'outils, souvent utilisées ensemble :

    ProvisioningGestion de configuration
    RôleCréer les ressources : réseau, VM, base managée, bucket, DNSConfigurer l'intérieur des serveurs : paquets, fichiers, services
    OutilsTerraform, OpenTofu, CloudFormation, Pulumi, BicepAnsible, Puppet, Chef, Salt
    Terraform en bref Terraform est un outil d'IaC déclaratif créé par HashiCorp (aujourd'hui dans le groupe IBM). Il est multi-cloud : grâce à ses milliers de providers, il pilote AWS, Azure, GCP, mais aussi Kubernetes, GitHub, Datadog, Dynatrace, Cloudflare et bien d'autres, avec un seul langage et un seul flux de travail.

    Points clés

    • IaC = infrastructure décrite dans du code versionné, relu et reproductible.
    • Terraform est déclaratif : on décrit l'état final, l'outil calcule les actions.
    • Idempotence : réappliquer la même configuration ne change rien.
    • Terraform sert au provisioning ; Ansible et ses équivalents, à la configuration.
    Module 2

    Premiers pas : HCL, providers, ressources et cycle de travail

    Le langage HCL

    Terraform utilise HCL (HashiCorp Configuration Language), un langage lisible conçu pour décrire de la configuration. Les fichiers portent l'extension .tf. Terraform lit tous les fichiers .tf d'un répertoire : leur découpage (main.tf, variables.tf, outputs.tf…) n'est qu'une convention de lisibilité.

    # versions.tf : version de Terraform et providers requis
terraform {
  required_version = ">= 1.6"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
  }
}

# Configuration du provider
provider "aws" {
  region = "eu-west-3"  # Paris
}

# Une ressource : type "aws_s3_bucket", nom local "logs"
resource "aws_s3_bucket" "logs" {
  bucket = "acme-prod-logs"
  tags = {
    environment = "prod"
  }
}

    Les blocs essentiels

    🔌 provider

    Un plugin qui sait parler à une API (AWS, Azure, Kubernetes…). Il est téléchargé depuis le Terraform Registry.

    🧱 resource

    Un objet que Terraform crée et gère : VM, bucket, enregistrement DNS… Adresse : type.nom.

    🔎 data

    Une data source lit une information existante sans la gérer : une image, un réseau créé ailleurs, un compte.

    ⚙️ terraform

    Les réglages de Terraform lui-même : versions, providers requis, backend du state.

    # Data source : lire la dernière image Ubuntu 24.04 publiée par Canonical
data "aws_ami" "ubuntu" {
  most_recent = true
  owners      = ["099720109477"]
  filter {
    name   = "name"
    values = ["ubuntu/images/hvm-ssd-gp3/ubuntu-noble-24.04-amd64-server-*"]
  }
}

resource "aws_instance" "web" {
  ami           = data.aws_ami.ubuntu.id   # référence à la data source
  instance_type = "t3.micro"
}

    Le cycle de travail

    CommandeRôle
    terraform initPrépare le répertoire : télécharge les providers et les modules, configure le backend du state. À relancer quand on ajoute un provider, un module ou qu'on change de backend.
    terraform fmtFormate le code selon le style standard.
    terraform validateVérifie la syntaxe et la cohérence interne de la configuration.
    terraform planCompare la configuration, le state et l'infrastructure réelle, puis affiche les changements prévus, sans rien modifier.
    terraform applyExécute les changements après confirmation, puis met à jour le state.
    terraform destroyDétruit toutes les ressources gérées par la configuration.

    Lire un plan

    Terraform will perform the following actions:

  # aws_s3_bucket.logs will be created
  + resource "aws_s3_bucket" "logs" { ... }

  # aws_instance.web will be updated in-place
  ~ resource "aws_instance" "web" {
      ~ instance_type = "t3.micro" -> "t3.small"
    }

  # aws_db_instance.main must be replaced
-/+ resource "aws_db_instance" "main" { ... }

Plan: 2 to add, 1 to change, 1 to destroy.
    Lisez toujours le plan + création, ~ modification sur place, - destruction, -/+ remplacement (destruction puis recréation). Un -/+ sur une base de données ou un disque peut signifier une perte de données : c'est le symbole à surveiller en priorité.

    Le fichier de verrouillage des providers

    terraform init crée le fichier .terraform.lock.hcl, qui fige les versions exactes et les empreintes (checksums) des providers. Il doit être commité dans Git pour que toute l'équipe et la CI utilisent exactement les mêmes versions. Le répertoire .terraform/, lui, ne se commite pas.

    Points clés

    • HCL, fichiers .tf ; Terraform lit tout le répertoire.
    • resource = géré par Terraform ; data = lu seulement.
    • Cycle : init → plan → apply (→ destroy).
    • Surveillez les remplacements -/+ ; commitez .terraform.lock.hcl.
    Module 3

    Variables, locals, outputs et expressions

    Variables d'entrée

    Les variables rendent une configuration réutilisable. Elles ont un type, une description, éventuellement une valeur par défaut et des règles de validation.

    variable "instance_count" {
  type        = number
  default     = 2
  description = "Nombre d'instances web"

  validation {
    condition     = var.instance_count > 0 && var.instance_count <= 10
    error_message = "Le nombre d'instances doit être compris entre 1 et 10."
  }
}

variable "db_password" {
  type      = string
  sensitive = true   # masqué dans l'affichage du plan et des logs
}

    Types disponibles : string, number, bool, et les types complexes list(...), set(...), map(...), object({...}), tuple([...]).

    Donner une valeur aux variables

    Par ordre de priorité croissante (la dernière source l'emporte) :

    1. la valeur default de la déclaration ;
    2. les variables d'environnement TF_VAR_nom ;
    3. le fichier terraform.tfvars (puis terraform.tfvars.json) ;
    4. les fichiers *.auto.tfvars, par ordre alphabétique ;
    5. les options en ligne de commande -var et -var-file : priorité la plus haute.
    terraform plan -var-file="prod.tfvars" -var="instance_count=4"

    Locals

    Les locals sont des valeurs calculées, internes à la configuration, qui évitent les répétitions :

    locals {
  name_prefix = "${var.project}-${var.environment}"
  common_tags = {
    project     = var.project
    environment = var.environment
    managed_by  = "terraform"
  }
}

    Outputs

    Les outputs exposent des valeurs après l'apply : pour les afficher, pour les passer à un autre module, ou pour qu'un outil externe les lise (terraform output -json).

    output "web_public_ip" {
  value       = aws_instance.web.public_ip
  description = "Adresse IP publique du serveur web"
}

    Créer plusieurs ressources : count et for_each

    # count : N copies identiques, adressées par index [0], [1], ...
resource "aws_instance" "web" {
  count         = var.instance_count
  ami           = data.aws_ami.ubuntu.id
  instance_type = "t3.micro"
  tags = { Name = "web-${count.index}" }
}

# for_each : une ressource par élément d'un map ou d'un set, adressée par clé
resource "aws_s3_bucket" "this" {
  for_each = toset(["logs", "backups", "exports"])
  bucket   = "acme-${each.key}"
}
    count ou for_each ? Avec count, supprimer un élément au milieu d'une liste décale tous les index suivants : Terraform veut alors détruire et recréer des ressources qui n'ont pas changé. Avec for_each, chaque ressource est identifiée par une clé stable (aws_s3_bucket.this["logs"]). Préférez for_each dès que les éléments sont distincts ; gardez count pour des copies identiques ou pour une création conditionnelle (count = var.enabled ? 1 : 0).

    Expressions utiles

    • Conditionnelle : var.env == "prod" ? "t3.large" : "t3.micro"
    • Expression for : { for k, b in aws_s3_bucket.this : k => b.arn }
    • Fonctions intégrées : merge(), lookup(), join(), cidrsubnet(), templatefile()…
    • Blocs dynamiques : dynamic "ingress" { for_each = ... } pour générer des sous-blocs répétés.

    La commande terraform console permet de tester ces expressions de façon interactive.

    Points clés

    • Variables = entrées ; locals = valeurs calculées internes ; outputs = sorties.
    • -var / -var-file en ligne de commande ont la priorité la plus haute.
    • sensitive = true masque une valeur à l'affichage.
    • Préférez for_each à count pour des éléments distincts.
    Module 4

    Le state : la mémoire de Terraform

    Le state (par défaut le fichier terraform.tfstate) est un fichier JSON qui fait le lien entre les ressources déclarées dans le code et les objets réels chez le fournisseur. Pour chaque ressource, il stocke son identifiant réel et ses attributs.

    Il sert à :

    • associer aws_instance.web à l'instance réelle i-0abc123… ;
    • calculer le plan : savoir ce qui existe déjà, ce qu'il faut créer, modifier ou supprimer ;
    • mémoriser les dépendances, par exemple pour détruire les ressources dans le bon ordre ;
    • améliorer les performances sur les grosses infrastructures.
    Le state contient des secrets en clair Mots de passe de base de données, clés générées, certificats… sensitive = true masque ces valeurs à l'affichage, mais elles restent stockées en clair dans le state. Il ne faut donc jamais commiter le state dans Git, et il faut le stocker dans un emplacement chiffré avec un accès restreint.

    Le backend distant

    En local, le state est un simple fichier sur un poste. Dès qu'on travaille à plusieurs ou en CI, il faut un backend distant : S3, Azure Blob Storage, Google Cloud Storage, HCP Terraform, GitLab…

    terraform {
  backend "s3" {
    bucket       = "acme-terraform-state"
    key          = "network/prod/terraform.tfstate"
    region       = "eu-west-3"
    encrypt      = true
    use_lockfile = true   # verrouillage natif S3 (Terraform 1.10 et +)
  }
}

    🤝 Partage

    Toute l'équipe et la CI travaillent sur le même state, toujours à jour.

    🔒 Verrouillage

    Le state locking empêche deux apply simultanés de corrompre le state.

    🛡️ Sécurité

    Chiffrement au repos, droits d'accès contrôlés, versioning du bucket pour restaurer une version précédente.

    Sur S3, le verrouillage passait historiquement par une table DynamoDB. Depuis Terraform 1.10, il peut se faire directement dans S3 avec use_lockfile.

    La dérive (drift)

    On parle de dérive quand l'infrastructure réelle ne correspond plus au code, en général parce que quelqu'un l'a modifiée à la main dans la console. Au plan suivant, Terraform la détecte et propose de revenir à ce que dit le code.

    • terraform plan : montre la dérive et les corrections prévues ;
    • terraform apply -refresh-only : met à jour le state avec la réalité, sans toucher à l'infrastructure (remplace l'ancienne commande terraform refresh).

    Les commandes de manipulation du state

    CommandeUsage
    terraform state listLister les ressources suivies
    terraform state show <adresse>Afficher les attributs d'une ressource
    terraform state mvRenommer ou déplacer une ressource dans le state (préférez le bloc moved, voir module 7)
    terraform state rmArrêter de gérer une ressource sans la détruire
    terraform importFaire entrer une ressource existante dans le state (préférez le bloc import)
    Règle d'or Ne modifiez jamais le fichier de state à la main. Passez par les commandes terraform state ou, mieux, par des blocs moved, import et removed qui sont relus en merge request.

    Points clés

    • Le state relie le code aux ressources réelles.
    • Il contient des secrets en clair : jamais dans Git, toujours chiffré.
    • En équipe : backend distant + verrouillage.
    • Dérive = modification hors Terraform, détectée au plan.
    Module 5

    Les modules : factoriser et réutiliser

    Un module est simplement un répertoire de fichiers .tf. Le répertoire depuis lequel on lance Terraform est le module racine (root module) ; il peut appeler des modules enfants (child modules), un peu comme une fonction appelle d'autres fonctions.

    Structure type d'un module

    modules/
└── web-app/
    ├── main.tf        # ressources
    ├── variables.tf   # entrées du module
    ├── outputs.tf     # sorties du module
    ├── versions.tf    # contraintes de versions
    └── README.md      # documentation et exemple d'usage

    Appeler un module

    # Module public du Terraform Registry, version figée
module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "~> 6.0"

  name = "prod"
  cidr = "10.0.0.0/16"
}

# Module local, qui utilise une sortie du module précédent
module "app" {
  source     = "./modules/web-app"
  subnet_ids = module.vpc.private_subnets
}

    Un module ne voit que ses variables et n'expose que ses outputs : c'est son interface. Les sources possibles sont un chemin local, le Terraform Registry public, un registre privé, un dépôt Git (git::https://…?ref=v1.2.0) ou une archive HTTP.

    Les contraintes de version

    ContrainteSignification
    = 1.2.0Exactement cette version
    >= 1.2.0Cette version ou une plus récente
    ~> 1.2.0≥ 1.2.0 et < 1.3.0 : seulement les correctifs
    ~> 1.2≥ 1.2 et < 2.0 : versions mineures et correctifs

    L'opérateur ~> (« pessimiste ») n'autorise que l'incrément du dernier chiffre indiqué. Pour un module Git, on fige la version avec un tag : ?ref=v1.2.0.

    Concevoir de bons modules

    • Un module doit correspondre à un concept cohérent (« un réseau », « une application web », « une base de données »), pas à une seule ressource.
    • Exposer peu de variables, avec des valeurs par défaut sensées et des validations.
    • Documenter les entrées et sorties (l'outil terraform-docs génère le README).
    • Versionner les modules partagés et figer les versions chez les utilisateurs.
    • Éviter les imbrications trop profondes : deux niveaux de modules suffisent en général.
    • Ne pas déclarer de bloc provider dans un module réutilisable : c'est le module racine qui configure les providers.

    Points clés

    • Module = répertoire de .tf ; interface = variables + outputs.
    • Sources : local, Registry, Git, registre privé.
    • Toujours figer les versions des modules partagés.
    • ~> 1.2 autorise 1.x à partir de 1.2, mais pas 2.0.
    Module 6

    Environnements, organisation du code et écosystème

    Gérer plusieurs environnements

    Il faut presque toujours déployer la même infrastructure en dev, recette et production. Deux approches principales existent :

    Un répertoire par environnementWorkspaces Terraform (CLI)
    Principeenvs/dev, envs/prod… qui appellent les mêmes modules avec des valeurs différentes, chacun avec son propre backend.Une seule configuration, plusieurs states (terraform workspace new prod) ; on distingue avec terraform.workspace.
    AvantagesIsolation forte, droits distincts par environnement, différences explicites.Peu de duplication, mise en place rapide.
    LimitesUn peu de code répété (atténué par les modules).Même backend et mêmes droits pour tous les environnements ; on se trompe facilement de workspace.

    Pour la production, l'approche un répertoire (ou un dépôt) par environnement est en général préférée, car elle isole mieux les droits et réduit le risque d'erreur.

    Découper le state

    Un state unique pour toute l'entreprise devient lent, risqué et source de conflits. On découpe par domaine et par cycle de vie : réseau, données, applications, supervision… Chaque partie a son propre state. On lit les sorties d'une autre partie avec la data source terraform_remote_state, ou mieux, avec des data sources du provider (rechercher un VPC par tag par exemple).

    Le rayon d'impact Plus un state est petit, plus le blast radius d'une erreur est limité : un apply raté sur le state « application » ne peut pas casser le réseau de production.

    L'écosystème

    ☁️ HCP Terraform

    Le service SaaS de HashiCorp (anciennement Terraform Cloud) : state distant, exécutions à distance, gestion des variables et secrets, politiques (Sentinel), registre privé. Une version auto-hébergée existe : Terraform Enterprise.

    🌿 OpenTofu

    En 2023, HashiCorp a remplacé la licence open source MPL de Terraform par la licence BSL. La communauté a créé OpenTofu, un fork open source hébergé par la Linux Foundation, largement compatible avec Terraform.

    🧰 Terragrunt

    Une surcouche qui limite la répétition entre environnements (configuration du backend, dépendances entre states).

    🔄 Autres orchestrateurs

    Atlantis, Spacelift, env0, Scalr, ou simplement GitLab CI / GitHub Actions pour exécuter plan et apply en équipe.

    Points clés

    • Production : un répertoire (et un backend) par environnement plutôt que des workspaces.
    • Découpez le state par domaine pour limiter le rayon d'impact.
    • HCP Terraform = service géré ; OpenTofu = fork open source après le passage à la licence BSL.
    Module 7

    Dépendances, cycle de vie et refactoring

    Le graphe de dépendances

    Terraform construit un graphe des ressources pour savoir dans quel ordre les créer, et lesquelles créer en parallèle.

    • Dépendance implicite : dès qu'une ressource référence un attribut d'une autre (subnet_id = aws_subnet.main.id), Terraform sait qu'il doit créer le sous-réseau d'abord. C'est le cas le plus courant.
    • Dépendance explicite : depends_on = [aws_iam_role_policy.app], à réserver aux cas où le lien n'apparaît pas dans les attributs (par exemple une application qui a besoin qu'une politique IAM existe avant de démarrer).

    terraform graph exporte ce graphe au format DOT (Graphviz).

    Le bloc lifecycle

    resource "aws_db_instance" "main" {
  # ...
  lifecycle {
    prevent_destroy       = true                    # refuse toute destruction
    create_before_destroy = true                    # crée le remplaçant avant de supprimer l'ancien
    ignore_changes        = [tags["last_backup"]]  # ignore les modifs faites ailleurs
  }
}
    OptionUsage typique
    prevent_destroyProtéger des ressources critiques (bases de données, clés de chiffrement) : toute action qui les détruirait fait échouer le plan.
    create_before_destroyÉviter une coupure lors d'un remplacement (certificat, groupe d'autoscaling).
    ignore_changesIgnorer un attribut modifié par un autre système (autoscaling, outil externe).
    replace_triggered_byForcer le remplacement quand une autre ressource change.
    precondition / postconditionVérifier des hypothèses avant ou après la création.

    Pour forcer ponctuellement le remplacement d'une ressource, on utilise terraform apply -replace="aws_instance.web" (qui remplace l'ancienne commande terraform taint).

    Refactoring sans destruction

    Renommer une ressource dans le code (aws_instance.web → aws_instance.frontend) fait croire à Terraform que l'ancienne doit être détruite et qu'une nouvelle doit être créée. Le bloc moved lui indique qu'il s'agit de la même ressource :

    moved {
  from = aws_instance.web
  to   = aws_instance.frontend
}

    Importer l'existant

    Pour gérer avec Terraform une ressource créée à la main, on utilise le bloc import (Terraform 1.5 et +), relu en merge request comme le reste du code :

    import {
  to = aws_s3_bucket.legacy
  id = "acme-legacy-bucket"
}

    terraform plan -generate-config-out=generated.tf peut même générer une première version du code HCL correspondant. Le bloc removed fait l'inverse : il retire une ressource de la gestion Terraform sans la détruire.

    Points clés

    • Les références entre ressources créent des dépendances implicites ; depends_on en dernier recours.
    • prevent_destroy protège ; create_before_destroy évite les coupures.
    • moved pour renommer, import pour reprendre l'existant, removed pour abandonner sans détruire.
    Module 8

    CI/CD, tests et sécurité

    Un pipeline type

    1. Sur chaque merge request : terraform fmt -check, terraform validate, analyse statique (tflint), scan de sécurité (Checkov, Trivy), tests.
    2. terraform plan -out=tfplan : le plan est publié en commentaire de la merge request pour être relu.
    3. Après validation et fusion : terraform apply tfplan applique exactement le plan relu, ni plus ni moins.
    4. Les applies se font depuis la CI uniquement, jamais depuis un poste de développeur.
    Pourquoi sauvegarder le plan ? Entre la revue et l'application, l'infrastructure ou le code peuvent avoir changé. Appliquer le fichier tfplan garantit que ce qui est exécuté est bien ce qui a été validé. Si l'état a changé entre-temps, Terraform refuse le plan devenu obsolète.

    Tester son code

    terraform validate

    Syntaxe et cohérence interne. Rapide, sans accès au cloud.

    tflint

    Erreurs probables et bonnes pratiques, par exemple un type d'instance inexistant.

    terraform test

    Framework de test natif (Terraform 1.6 et +) avec des fichiers .tftest.hcl.

    Terratest

    Tests d'intégration en Go : on déploie, on vérifie, on détruit.

    # tests/bucket.tftest.hcl
run "nom_du_bucket" {
  command = plan

  assert {
    condition     = aws_s3_bucket.logs.bucket == "acme-prod-logs"
    error_message = "Nom de bucket inattendu"
  }
}

    Sécurité

    • Pas de secrets dans le code : utilisez un coffre-fort (Vault, AWS Secrets Manager, Azure Key Vault) lu par data source, ou des variables d'environnement injectées par la CI.
    • Pas d'identifiants longue durée en CI : préférez l'authentification par OIDC (fédération d'identité de la CI vers le cloud).
    • Moindre privilège : un rôle par pipeline, limité à ce qu'il gère ; séparer les droits de plan (lecture) et d'apply (écriture).
    • Protéger le state : chiffrement, accès restreint, versioning.
    • Scanner le code : Checkov et Trivy détectent les erreurs de configuration (bucket public, chiffrement désactivé, port 22 ouvert à Internet…).
    • Policy as code : Sentinel (HCP Terraform) ou OPA / Conftest pour imposer des règles d'entreprise sur le plan, par exemple « pas de ressource sans tag owner » ou « uniquement les régions européennes ».

    Points clés

    • fmt, validate, lint, scan et plan sur chaque merge request.
    • On applique le plan relu (apply tfplan), depuis la CI uniquement.
    • Aucun secret dans le code ; OIDC plutôt que des clés statiques.
    • La policy as code (Sentinel, OPA) rend les règles d'entreprise automatiques.
    Module 9

    Bonnes pratiques

    Code

    • Conventions de nommage : snake_case pour les noms Terraform, nom unique this ou main quand il n'y a qu'une ressource d'un type.
    • Découpage des fichiers : versions.tf, providers.tf, variables.tf, main.tf, outputs.tf.
    • Figer les versions de Terraform, des providers et des modules ; commiter .terraform.lock.hcl.
    • Taguer toutes les ressources (projet, environnement, propriétaire, managed_by = terraform), par exemple avec default_tags du provider AWS.
    • Décrire et valider les variables ; marquer les valeurs sensibles avec sensitive.
    • Ne pas en faire trop : un code simple et explicite vaut mieux que des abstractions trop astucieuses.

    Organisation

    • Tout passe par le code : aucune modification manuelle en console, sinon il y aura de la dérive.
    • Des states petits et découpés par domaine et par environnement.
    • Un backend distant chiffré, avec verrouillage et versioning.
    • Des modules partagés versionnés, dans un registre interne.
    • Un pipeline CI/CD unique pour plan et apply.
    • Une détection régulière de la dérive (un plan planifié chaque nuit, par exemple).
    Pièges courants
    • State local ou commité dans Git, avec des secrets dedans.
    • Utiliser count sur une liste qui évolue, ce qui recrée des ressources inutilement.
    • Lancer un apply sans lire le plan, ou avec -auto-approve sur un poste local.
    • Renommer une ressource sans bloc moved, ce qui la détruit puis la recrée.
    • Ne pas figer les versions de providers : un init le lundi ne donne plus le même résultat que le vendredi.
