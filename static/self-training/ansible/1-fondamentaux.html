    Bienvenue

    Ansible et l'automatisation de configuration

    Cette formation présente la gestion de configuration et l'utilisation d'Ansible pour automatiser l'installation, la configuration et le déploiement sur des parcs de serveurs. Elle se termine par un quiz de validation des connaissances.

    ⏱️ Durée

    Environ 1 h 30 de lecture, plus 20 minutes de quiz.

    🎯 Public

    Administrateurs système, développeurs, ops, SRE et toute personne qui gère des serveurs.

    ✅ Validation

    Un quiz de 20 questions. Seuil de réussite : 80 %.

    Objectifs pédagogiques

    À l'issue de cette formation, vous saurez :

    • expliquer le principe de la gestion de configuration et le fonctionnement sans agent d'Ansible ;
    • écrire un inventaire et lancer des commandes ad hoc ;
    • écrire des playbooks idempotents avec tâches, modules et handlers ;
    • utiliser les variables, facts et templates Jinja2 ;
    • organiser le code en rôles et utiliser les collections ;
    • protéger les secrets avec Ansible Vault ;
    • tester et exécuter Ansible à l'échelle (ansible-lint, Molecule, AWX / Automation Platform).

    Module 1

    La gestion de configuration et les principes d'Ansible

    La gestion de configuration consiste à décrire dans du code l'état attendu des serveurs (paquets installés, fichiers de configuration, services démarrés, utilisateurs…) et à laisser un outil appliquer cet état de façon automatique, reproductible et traçable. On évite ainsi les procédures manuelles et les serveurs qui divergent avec le temps.

    Les atouts d'Ansible

    🚫 Sans agent

    Rien à installer sur les machines gérées : Ansible se connecte en SSH (ou WinRM / SSH pour Windows). Il faut seulement Python sur les hôtes Linux.

    📄 YAML lisible

    Les playbooks sont écrits en YAML : ils se lisent presque comme une procédure, y compris par des non-développeurs.

    📤 Mode push

    Le poste de contrôle envoie les instructions au moment voulu, sans serveur central obligatoire.

    🧩 Très large couverture

    Des milliers de modules : Linux, Windows, réseau, cloud, bases de données, conteneurs.

    Idempotence

    Comme Terraform, Ansible est conçu pour être idempotent : on décrit un état (« le paquet nginx doit être présent »), pas une action (« installe nginx »). Si l'état est déjà atteint, la tâche ne fait rien et renvoie ok ; sinon elle agit et renvoie changed. On peut donc relancer un playbook autant de fois que l'on veut.

    Attention aux modules command et shell command et shell exécutent une commande à chaque fois et renvoient toujours changed : ils ne sont pas idempotents par nature. Utilisez un module dédié dès qu'il en existe un. Sinon, rendez la tâche idempotente avec creates, removes ou changed_when.

    Ansible face aux autres outils

    AnsiblePuppet / ChefTerraform
    Usage principalConfiguration, déploiement, orchestrationConfigurationProvisioning d'infrastructure
    AgentNon (SSH)Oui (agent sur chaque nœud)Non (appels d'API)
    ModèlePushPull (l'agent interroge un serveur)Push
    StateAucun : l'état est relu sur les machines à chaque exécutionSur le serveur centralFichier de state
    LangageYAML + Jinja2DSL dédié / RubyHCL
    Terraform et Ansible sont complémentaires Terraform crée les machines, réseaux et services cloud ; Ansible configure ce qui tourne à l'intérieur des machines. Le module 9 montre comment les combiner.

    Points clés

    • Ansible : sans agent, via SSH, en mode push, en YAML.
    • Idempotence : on décrit un état ; ok = rien à faire, changed = modifié.
    • command et shell ne sont pas idempotents par défaut.
    • Ansible configure ; Terraform provisionne.
    Module 2

    Architecture et inventaire

    • Nœud de contrôle (control node) : la machine où Ansible est installé et d'où on lance les commandes (un poste Linux ou macOS, un conteneur, un serveur d'automatisation). Windows ne peut pas servir de nœud de contrôle, sauf via WSL.
    • Nœuds gérés (managed nodes) : les machines que l'on configure.
    • Pour chaque tâche, Ansible envoie un petit programme (le module) sur l'hôte, l'exécute avec Python, récupère le résultat en JSON, puis le supprime.

    L'inventaire

    L'inventaire liste les hôtes gérés et les range en groupes. Il peut être écrit en INI ou en YAML.

    # inventory.ini
[webservers]
web[1:3].example.com

[dbservers]
db1.example.com  ansible_user=admin

[prod:children]
webservers
dbservers
    # inventory.yml : équivalent en YAML
all:
  children:
    webservers:
      hosts:
        web1.example.com:
        web2.example.com:
        web3.example.com:
    dbservers:
      hosts:
        db1.example.com:
          ansible_user: admin
    • Deux groupes existent toujours implicitement : all (tous les hôtes) et ungrouped.
    • Des variables de connexion spéciales règlent l'accès : ansible_host, ansible_user, ansible_port, ansible_connection…
    • Les variables d'inventaire se rangent de préférence dans les répertoires group_vars/ et host_vars/.

    Les inventaires dynamiques

    Dans le cloud, les serveurs apparaissent et disparaissent en permanence. Un inventaire dynamique (plugin d'inventaire) interroge une source à jour (AWS, Azure, GCP, VMware, une CMDB…) et construit les groupes automatiquement, par exemple à partir des tags des machines.

    # aws_ec2.yml : plugin d'inventaire de la collection amazon.aws
plugin: amazon.aws.aws_ec2
regions:
  - eu-west-3
keyed_groups:
  - key: tags.role       # crée les groupes role_web, role_db...
    prefix: role

    La commande ansible-inventory -i inventory.yml --graph affiche l'arborescence des groupes et des hôtes.

    Le fichier ansible.cfg

    Il fixe les réglages par défaut du projet : chemin de l'inventaire, utilisateur distant, nombre de connexions parallèles (forks, 5 par défaut), chemin des rôles… Ansible le cherche dans cet ordre : variable ANSIBLE_CONFIG, ./ansible.cfg (répertoire courant), ~/.ansible.cfg, puis /etc/ansible/ansible.cfg.

    Points clés

    • Nœud de contrôle → SSH → nœuds gérés, en parallèle (forks).
    • Inventaire = hôtes rangés en groupes, en INI ou en YAML.
    • Inventaire dynamique pour le cloud et les environnements qui changent.
    • ansible.cfg du projet pour des réglages partagés.
    Module 3

    Commandes ad hoc et modules

    Les commandes ad hoc

    Une commande ad hoc exécute un seul module sur un ensemble d'hôtes, directement depuis la ligne de commande. C'est pratique pour une action ponctuelle ; pour tout ce qui doit être rejoué ou relu, on écrit un playbook.

    # Tester la connexion et la présence de Python sur tous les hôtes
ansible all -i inventory.ini -m ansible.builtin.ping

# Installer un paquet sur le groupe webservers, avec élévation de privilèges
ansible webservers -m ansible.builtin.package -a "name=htop state=present" --become

# Redémarrer un service
ansible dbservers -m ansible.builtin.service -a "name=postgresql state=restarted" --become

# Collecter des informations (facts) sur les hôtes
ansible all -m ansible.builtin.setup -a "filter=ansible_distribution*"
    Le module ping n'est pas un ping réseau ansible.builtin.ping n'envoie pas de paquet ICMP : il vérifie qu'Ansible peut se connecter à l'hôte (SSH, authentification) et y exécuter Python. Il répond pong en cas de succès.

    Les modules les plus utilisés

    ModuleRôle
    ansible.builtin.package, apt, dnfInstaller ou supprimer des paquets
    ansible.builtin.copyCopier un fichier tel quel vers les hôtes
    ansible.builtin.templateGénérer un fichier à partir d'un modèle Jinja2 et de variables
    ansible.builtin.fileGérer fichiers, répertoires, liens et permissions
    ansible.builtin.lineinfileGarantir la présence (ou l'absence) d'une ligne dans un fichier
    ansible.builtin.service / systemd_serviceDémarrer, arrêter, activer des services
    ansible.builtin.user / groupGérer les comptes et les groupes
    ansible.builtin.command / shellExécuter une commande (dernier recours, voir module 1)
    ansible.builtin.uriAppeler une API HTTP

    command exécute directement le programme, sans passer par un shell : pas de pipes, de redirections ni de variables d'environnement. shell passe par /bin/sh et accepte tout cela, mais il expose davantage aux erreurs d'échappement et aux injections. Préférez command quand le shell n'est pas nécessaire.

    Les noms complets (FQCN)

    Depuis Ansible 2.10, les modules sont distribués dans des collections. On les désigne par leur nom complet (FQCN, Fully Qualified Collection Name) : espace_de_noms.collection.module, par exemple ansible.builtin.copy ou community.general.timezone. Le nom court (copy) fonctionne encore, mais le FQCN évite toute ambiguïté entre modules homonymes et c'est la pratique recommandée.

    La documentation de chaque module est disponible hors ligne : ansible-doc ansible.builtin.template.

    Points clés

    • Ad hoc = un module, une fois, depuis la ligne de commande.
    • ping teste la connexion et Python, pas le réseau ICMP.
    • Utilisez un module dédié plutôt que command / shell.
    • Utilisez les noms complets (FQCN) : ansible.builtin.copy.
    Module 4

    Les playbooks

    Un playbook est un fichier YAML qui contient un ou plusieurs plays. Un play associe un groupe d'hôtes (hosts) à une liste de tâches exécutées dans l'ordre. Chaque tâche appelle un module.

    # site.yml
- name: Installer et configurer nginx
  hosts: webservers
  become: true                # élévation de privilèges (sudo)
  vars:
    http_port: 80

  tasks:
    - name: Installer nginx
      ansible.builtin.package:
        name: nginx
        state: present

    - name: Déployer la configuration
      ansible.builtin.template:
        src: templates/nginx.conf.j2
        dest: /etc/nginx/nginx.conf
        mode: "0644"
      notify: Recharger nginx   # déclenche le handler si changed

    - name: Démarrer nginx et l'activer au boot
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: true

  handlers:
    - name: Recharger nginx
      ansible.builtin.service:
        name: nginx
        state: reloaded

    Exécution

    ansible-playbook -i inventory.ini site.yml

# Simulation : affiche ce qui changerait, sans rien modifier
ansible-playbook -i inventory.ini site.yml --check --diff

# Limiter à un hôte, n'exécuter que certaines tâches
ansible-playbook site.yml --limit web1.example.com --tags config

    Lire le résultat

    PLAY RECAP *********************************************************
web1.example.com : ok=4  changed=1  unreachable=0  failed=0  skipped=0
web2.example.com : ok=4  changed=0  unreachable=0  failed=0  skipped=0
    StatutSignification
    okLa tâche a réussi ; l'état était déjà conforme, rien n'a changé
    changedLa tâche a modifié quelque chose sur l'hôte
    failedLa tâche a échoué ; par défaut, l'hôte est retiré du reste du play
    skippedLa tâche n'a pas été exécutée (condition when fausse)
    unreachableAnsible n'a pas pu se connecter à l'hôte
    Le test d'idempotence Lancez le playbook deux fois : au second passage, toutes les tâches doivent être en ok, avec changed=0. Sinon, une tâche n'est pas idempotente.

    Les handlers

    Un handler est une tâche qui ne s'exécute que si une autre tâche l'a notifiée (notify) et a renvoyé changed. Les handlers s'exécutent à la fin du play et une seule fois, même s'ils ont été notifiés par plusieurs tâches. Usage type : recharger un service uniquement si sa configuration a changé. Pour les déclencher plus tôt, on utilise ansible.builtin.meta: flush_handlers.

    Autres notions utiles

    • become : exécuter avec des droits élevés (sudo par défaut), au niveau du play ou d'une tâche, avec become_user pour choisir l'utilisateur.
    • tags : étiqueter des tâches pour n'en exécuter qu'une partie (--tags, --skip-tags).
    • --check (dry run) et --diff (afficher les différences de fichiers) : indispensables avant d'appliquer en production.
    • --start-at-task et --step : reprendre ou avancer pas à pas.

    Points clés

    • Playbook → plays → tâches → modules.
    • Handlers : exécutés à la fin du play, une seule fois, uniquement si notifiés par une tâche changed.
    • --check --diff pour simuler avant d'appliquer.
    • Second passage = changed=0 si le playbook est idempotent.
    Module 5

    Variables, facts, templates et logique

    Où définir des variables ?

    projet/
├── inventory.ini
├── group_vars/
│   ├── all.yml          # tous les hôtes
│   └── webservers.yml   # groupe webservers
├── host_vars/
│   └── web1.example.com.yml
└── site.yml

    La priorité des variables

    Ansible compte plus de 20 niveaux de priorité. Voici une version simplifiée, de la plus faible à la plus forte :

    1. defaults/ d'un rôle (prévu pour être surchargé) ;
    2. variables d'inventaire : group_vars/all, puis group_vars/<groupe>, puis host_vars/<hôte> ;
    3. facts collectés sur l'hôte ;
    4. vars du play, vars_files ;
    5. vars/ d'un rôle ;
    6. variables de tâche, set_fact et register ;
    7. extra vars passées avec -e en ligne de commande : elles l'emportent toujours.
    Règle pratique Définissez chaque variable à un seul endroit, le plus simple possible. Mettez les valeurs par défaut dans defaults/ des rôles, et les valeurs propres à un environnement dans group_vars.

    Les facts

    Au début de chaque play, Ansible exécute le module setup pour collecter des facts sur chaque hôte : système d'exploitation, version, adresses IP, mémoire, disques… Ils sont accessibles via ansible_facts, par exemple ansible_facts['distribution'] ou ansible_facts['default_ipv4']['address']. On peut désactiver la collecte avec gather_facts: false pour gagner du temps quand on n'en a pas besoin.

    Templates Jinja2

    Ansible utilise le moteur Jinja2 pour insérer des variables ({{ variable }}), écrire des boucles et des conditions ({% ... %}) et appliquer des filtres.

    # templates/nginx.conf.j2
server {
    listen {{ http_port }};
    server_name {{ inventory_hostname }};

{% for backend in backends %}
    # backend : {{ backend }}
{% endfor %}
    client_max_body_size {{ max_upload | default('10m') }};
}

    Quelques filtres courants : default, upper, join, to_nice_yaml, password_hash, bool…

    Attention aux guillemets en YAML Une valeur YAML qui commence par {{ doit être entre guillemets : name: "{{ item }}". Sinon, YAML l'interprète comme un dictionnaire et le playbook échoue.

    Conditions, boucles et register

    - name: Vérifier si l'application est installée
  ansible.builtin.stat:
    path: /opt/app/bin/app
  register: app_bin                 # stocke le résultat de la tâche

- name: Installer l'application si elle est absente
  ansible.builtin.unarchive:
    src: app.tar.gz
    dest: /opt/app
  when: not app_bin.stat.exists     # condition

- name: Créer les comptes utilisateurs
  ansible.builtin.user:
    name: "{{ item }}"
    state: present
  loop:                             # boucle
    - alice
    - bob

- name: Installer les paquets Debian uniquement
  ansible.builtin.apt:
    name: [curl, git]
    state: present
  when: ansible_facts['os_family'] == "Debian"

    Points clés

    • Les extra vars (-e) ont la priorité la plus haute ; les defaults/ de rôle, la plus basse.
    • Facts = informations collectées sur l'hôte (ansible_facts).
    • Jinja2 : {{ variable }}, {% for %}, filtres ; mettez les guillemets en YAML.
    • register stocke un résultat, when conditionne, loop répète.
    Module 6

    Rôles et collections

    Les rôles

    Un rôle regroupe tout ce qui sert à configurer une fonctionnalité (tâches, handlers, templates, fichiers, variables) dans une arborescence standard. Il est réutilisable d'un projet à l'autre et se partage facilement.

    roles/
└── nginx/
    ├── defaults/main.yml    # variables par défaut (priorité la plus faible)
    ├── vars/main.yml        # variables internes (priorité élevée)
    ├── tasks/main.yml       # point d'entrée des tâches
    ├── handlers/main.yml    # handlers
    ├── templates/           # modèles Jinja2 (.j2)
    ├── files/               # fichiers copiés tels quels
    └── meta/main.yml        # métadonnées, dépendances

    La commande ansible-galaxy role init nginx crée ce squelette. On utilise ensuite le rôle dans un playbook :

    - name: Serveurs web
  hosts: webservers
  become: true
  roles:
    - role: nginx
      vars:
        http_port: 8080

    On peut aussi inclure un rôle au milieu des tâches avec ansible.builtin.import_role (statique, résolu au chargement) ou ansible.builtin.include_role (dynamique, résolu à l'exécution).

    Les collections

    Une collection est le format de distribution du contenu Ansible : elle regroupe des modules, des plugins, des rôles et des playbooks sous un espace de noms (community.general, amazon.aws, ansible.windows, kubernetes.core…).

    • Le paquet ansible-core ne contient que le moteur et la collection ansible.builtin.
    • Le paquet ansible (dit « communautaire ») inclut en plus une large sélection de collections.
    • Ansible Galaxy est le dépôt public de rôles et de collections ; les entreprises utilisent souvent un hub privé (Automation Hub, Private Automation Hub, ou un dépôt Galaxy interne).

    Les dépendances d'un projet se déclarent dans un fichier requirements.yml, avec des versions figées :

    # requirements.yml
collections:
  - name: community.general
    version: ">=9.0.0,<10.0.0"
  - name: amazon.aws
roles:
  - name: geerlingguy.docker
    version: "7.4.1"
    ansible-galaxy install -r requirements.yml

    Points clés

    • Rôle = arborescence standard (tasks, handlers, templates, defaults…), réutilisable.
    • defaults/ pour ce que l'utilisateur peut surcharger, vars/ pour l'interne.
    • Collection = format de distribution des modules, plugins et rôles.
    • requirements.yml + versions figées pour des exécutions reproductibles.
    Module 7

    Secrets et sécurité

    Ansible Vault

    Ansible Vault chiffre (en AES-256) des fichiers ou des valeurs, qui peuvent ainsi être commités dans Git sans exposer les secrets. Ansible les déchiffre en mémoire au moment de l'exécution.

    # Créer, éditer, chiffrer, afficher un fichier chiffré
ansible-vault create group_vars/prod/vault.yml
ansible-vault edit   group_vars/prod/vault.yml
ansible-vault encrypt secrets.yml
ansible-vault view   secrets.yml

# Chiffrer une seule valeur, à coller dans un fichier de variables
ansible-vault encrypt_string 'S3cr3t!' --name 'db_password'

# Exécuter un playbook qui utilise des données chiffrées
ansible-playbook site.yml --ask-vault-pass
ansible-playbook site.yml --vault-password-file ~/.vault_pass
    Une convention utile Dans group_vars/prod/, placez un fichier vars.yml en clair qui référence des variables préfixées vault_, définies dans un fichier vault.yml chiffré :
    db_password: "{{ vault_db_password }}".
    On voit ainsi quelles variables existent (avec grep, par exemple) sans pouvoir lire leurs valeurs.

    On peut aussi utiliser plusieurs mots de passe Vault avec des identifiants (--vault-id dev@prompt --vault-id prod@~/.vault_prod), ou récupérer les secrets directement depuis un coffre-fort externe (HashiCorp Vault, CyberArk, AWS Secrets Manager, Azure Key Vault) grâce aux plugins de lookup.

    Éviter les fuites dans les logs

    Par défaut, Ansible affiche les paramètres et les résultats des tâches, notamment en mode verbeux (-v à -vvvv). Pour une tâche qui manipule un secret, ajoutez no_log: true :

    - name: Créer l'utilisateur de base de données
  community.postgresql.postgresql_user:
    name: app
    password: "{{ db_password }}"
  no_log: true

    Bonnes pratiques de sécurité

    • Authentification SSH par clé, jamais par mot de passe en clair dans l'inventaire.
    • Un compte de service dédié à l'automatisation, avec des droits sudo limités au nécessaire.
    • Le mot de passe Vault ne doit jamais se trouver dans le dépôt Git.
    • Vérifier les rôles et collections tiers avant de les utiliser, et figer leurs versions.
    • Utiliser validate sur les modules template et copy (par exemple validate: visudo -cf %s) pour ne jamais déployer un fichier de configuration invalide.

    Points clés

    • Ansible Vault chiffre fichiers et valeurs, qui peuvent ensuite aller dans Git.
    • no_log: true empêche l'affichage des secrets dans la sortie.
    • Clés SSH, compte dédié, moindre privilège, mot de passe Vault hors du dépôt.
    Module 8

    Robustesse, tests et exécution à l'échelle

    Gérer les erreurs

    - name: Mise à jour de l'application avec retour arrière
  block:
    - name: Déployer la nouvelle version
      ansible.builtin.unarchive:
        src: app-2.0.tar.gz
        dest: /opt/app
    - name: Vérifier l'état de santé
      ansible.builtin.uri:
        url: http://localhost:8080/health
        status_code: 200
      retries: 5
      delay: 3
      register: health
      until: health.status == 200
  rescue:                       # exécuté si une tâche du block échoue
    - name: Revenir à la version précédente
      ansible.builtin.unarchive:
        src: app-1.9.tar.gz
        dest: /opt/app
  always:                       # exécuté dans tous les cas
    - name: Nettoyer les fichiers temporaires
      ansible.builtin.file:
        path: /tmp/app-upgrade
        state: absent
    • ignore_errors: true : continuer malgré l'échec d'une tâche (à utiliser avec parcimonie).
    • failed_when / changed_when : définir soi-même ce qui compte comme un échec ou un changement.
    • retries / until : réessayer jusqu'à ce qu'une condition soit remplie.

    Déploiements progressifs

    • serial : traiter les hôtes par lots (serial: 2 ou serial: "25%") pour une mise à jour progressive (rolling update) sans couper tout le service.
    • max_fail_percentage : arrêter le déploiement si trop d'hôtes échouent.
    • delegate_to : exécuter une tâche sur une autre machine, par exemple retirer un serveur du load balancer avant de le mettre à jour.
    • run_once : exécuter une tâche une seule fois pour tout le groupe (une migration de base de données, par exemple).
    • strategy: free : laisser chaque hôte avancer à son rythme, au lieu d'attendre que tous aient terminé chaque tâche (stratégie linear, par défaut).

    Qualité et tests

    ansible-lint

    Analyse statique : bonnes pratiques, FQCN, noms de tâches, usage risqué de shell…

    yamllint

    Syntaxe et style YAML.

    --syntax-check

    ansible-playbook --syntax-check : vérification rapide de la syntaxe du playbook.

    Molecule

    Tests de rôles : crée des instances jetables (conteneurs, VM), applique le rôle, vérifie l'idempotence et le résultat, puis détruit tout.

    Exécuter à l'échelle

    🏢 Ansible Automation Platform

    L'offre de Red Hat : interface web et API (automation controller), droits par équipe (RBAC), gestion des identifiants, planification, journal d'audit, workflows.

    🌱 AWX

    Le projet open source en amont de l'automation controller, avec les mêmes concepts.

    📦 Execution Environments

    Des images de conteneurs qui embarquent ansible-core, Python et les collections. Elles sont construites avec ansible-builder et utilisées avec ansible-navigator, pour une exécution identique partout.

    🔄 CI/CD

    Lint et tests sur chaque merge request, puis exécution des playbooks depuis la CI ou le contrôleur, jamais depuis un poste personnel en production.

    Points clés

    • block / rescue / always pour gérer les erreurs et les retours arrière.
    • serial pour des mises à jour progressives.
    • ansible-lint et Molecule pour la qualité et les tests.
    • AWX / Automation Platform et Execution Environments pour l'échelle et la reproductibilité.
    Module 9

    Bonnes pratiques et combinaison avec Terraform

    Écriture

    • Nommez toutes les tâches (name:) : la sortie devient lisible et sert de documentation.
    • Utilisez les FQCN et des modules dédiés plutôt que command / shell.
    • Gardez des playbooks courts, qui appellent des rôles.
    • Écrivez le YAML de façon cohérente : true/false plutôt que yes/no, modes de fichier entre guillemets (mode: "0644").
    • Préfixez les variables d'un rôle par son nom (nginx_port) pour éviter les collisions.
    • Testez l'idempotence : un second passage doit donner changed=0.

    Organisation d'un projet

    ansible-projet/
├── ansible.cfg
├── requirements.yml
├── inventories/
│   ├── dev/
│   │   ├── hosts.yml
│   │   └── group_vars/
│   └── prod/
│       ├── hosts.yml
│       └── group_vars/
├── roles/
├── playbooks/
│   ├── site.yml
│   └── webservers.yml
└── .ansible-lint

    Un inventaire par environnement : on choisit la cible explicitement avec -i inventories/prod, ce qui limite le risque de lancer une modification sur le mauvais environnement.

    Terraform + Ansible

    1. Terraform crée le réseau, les machines virtuelles, les bases managées et les règles de pare-feu, et pose des tags sur les machines (role = web).
    2. Ansible récupère les machines avec un inventaire dynamique basé sur ces tags, ou à partir des outputs Terraform (terraform output -json).
    3. Ansible configure le système, déploie l'application et gère les mises à jour progressives.
    Variante immuable Ansible peut aussi servir à construire des images (avec Packer, par exemple). Terraform déploie ensuite ces images toutes prêtes : il n'y a plus de configuration à faire au démarrage des machines.
    Pièges courants
    • Des playbooks remplis de shell, donc non idempotents et toujours changed.
    • La même variable définie à cinq endroits, avec des priorités difficiles à comprendre.
    • Des secrets en clair dans group_vars, ou affichés dans les logs faute de no_log.
    • Des modifications manuelles sur les serveurs, écrasées au passage suivant d'Ansible (ou, pire, qui le font échouer).
    • Des collections et rôles tiers sans version figée.
