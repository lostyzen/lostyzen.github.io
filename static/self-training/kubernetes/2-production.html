    Cette deuxième partie aborde ce qu'il faut maîtriser pour faire tourner des applications de façon fiable, sûre et économique : ressources, santé, placement, réseau, stockage, sécurité, autoscaling, déploiement continu et dépannage. Elle se termine par un quiz de validation.

    Module 1

    Ressources et sondes de santé

    Requests et limits

    containers:
  - name: api
    image: ghcr.io/acme/api:1.4.0
    resources:
      requests:          # réservé : utilisé par le scheduler pour placer le pod
        cpu: "250m"       # 0,25 cœur
        memory: "256Mi"
      limits:            # plafond appliqué à l'exécution
        memory: "512Mi"
    RequestsLimits
    RôleQuantité réservée ; sert au placement par le schedulerQuantité maximale utilisable
    Dépassement CPUAutorisé si le nœud a du CPU libreLe conteneur est ralenti (throttling), pas tué
    Dépassement mémoireAutorisé, mais le pod devient candidat à l'éviction si le nœud manque de mémoireLe conteneur est tué : OOMKilled (code 137)
    Pratique courante Toujours définir des requests réalistes (mesurées, pas devinées). Pour la mémoire, une limit égale ou proche de la request évite les mauvaises surprises. Pour le CPU, beaucoup d'équipes ne mettent pas de limit pour éviter le throttling, à condition que les requests soient correctes.

    Les classes de qualité de service (QoS)

    • Guaranteed : requests = limits pour le CPU et la mémoire de tous les conteneurs. Dernier pod évincé en cas de pénurie.
    • Burstable : au moins une request ou une limit définie, sans remplir les conditions de Guaranteed.
    • BestEffort : ni request ni limit. Premier évincé ; à éviter en production.

    Au niveau d'un namespace, ResourceQuota plafonne la consommation totale (CPU, mémoire, nombre d'objets) et LimitRange impose des valeurs par défaut et des bornes aux conteneurs.

    Les sondes (probes)

    SondeQuestion poséeEn cas d'échec
    startupProbeL'application a-t-elle fini de démarrer ?Les autres sondes attendent ; après trop d'échecs, le conteneur est redémarré
    readinessProbeL'application est-elle prête à recevoir du trafic ?Le pod est retiré des Services (plus de trafic), mais n'est pas redémarré
    livenessProbeL'application est-elle encore vivante (pas bloquée) ?Le conteneur est redémarré
     
        readinessProbe:
      httpGet: { path: /health/ready, port: 8080 }
      periodSeconds: 5
    livenessProbe:
      httpGet: { path: /health/live, port: 8080 }
      periodSeconds: 10
      failureThreshold: 3
    Piège classique Une liveness qui vérifie les dépendances (base de données, API externe) est dangereuse : si la base tombe, tous les pods sont redémarrés en boucle, ce qui aggrave l'incident. La liveness ne doit tester que le processus lui-même ; les dépendances relèvent éventuellement de la readiness.

    Points clés

    • Requests = réservation et placement ; limits = plafond.
    • CPU dépassé → throttling ; mémoire dépassée → OOMKilled.
    • Readiness retire du trafic ; liveness redémarre ; startup protège les démarrages lents.

    Ordonnancement et haute disponibilité

    Contrôler le placement

    MécanismePrincipeExemple
    nodeSelectorLe pod ne va que sur les nœuds portant un labelUniquement sur des nœuds disktype=ssd
    Node affinityVersion plus riche : règles obligatoires (required) ou préférences (preferred)De préférence sur des instances Graviton
    Pod affinity / anti-affinityPlacer un pod près de, ou loin de, certains autres podsNe pas mettre deux réplicas de la base sur le même nœud
    Taints et tolerationsUn nœud « repousse » les pods (taint), sauf ceux qui le tolèrent (toleration)Nœuds GPU réservés aux pods de calcul
    Topology spread constraintsRépartir les réplicas équitablement entre zones ou nœudsRéplicas équilibrés sur 3 zones de disponibilité
    Ne pas confondre L'affinity attire un pod vers des nœuds ; le taint repousse les pods d'un nœud. Pour réserver des nœuds à une charge précise, on combine les deux : un taint sur les nœuds, et une toleration + une affinity sur les pods concernés.

    Répartir sur plusieurs zones

        topologySpreadConstraints:
      - maxSkew: 1
        topologyKey: topology.kubernetes.io/zone
        whenUnsatisfiable: DoNotSchedule
        labelSelector:
          matchLabels: { app: web }

    Avec 3 réplicas et 3 zones, chaque zone reçoit un réplica : la perte d'une zone entière n'emporte qu'un tiers de la capacité.

    Survivre aux maintenances : PodDisruptionBudget

    Les nœuds sont régulièrement vidés (kubectl drain) pour des mises à jour, du remplacement de machines ou de l'optimisation de coûts. Ces interruptions volontaires respectent le PodDisruptionBudget (PDB) :

    apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web
spec:
  minAvailable: 2          # ou maxUnavailable: 1
  selector:
    matchLabels: { app: web }

    Le drain attend alors qu'au moins 2 pods web restent disponibles avant d'en évincer un autre. Attention : un PDB trop strict (par exemple minAvailable égal au nombre de réplicas) bloque les drains et donc les mises à jour de nœuds.

    Check-list de haute disponibilité

    • Au moins 2 réplicas, idéalement 3, pour les services critiques.
    • Répartition multi-zones (topology spread ou anti-affinity).
    • Un PDB raisonnable.
    • Des sondes readiness correctes pour ne router que vers des pods prêts.
    • Un arrêt propre : l'application gère le signal SIGTERM et termine ses requêtes en cours dans le délai terminationGracePeriodSeconds (30 s par défaut).

    Points clés

    • nodeSelector / affinity attirent ; taints repoussent, tolerations autorisent.
    • Topology spread constraints pour répartir les réplicas entre zones.
    • PDB pour limiter l'impact des maintenances, sans bloquer les drains.
    Module 3

    Le réseau dans Kubernetes

    Le modèle réseau

    Kubernetes impose un modèle simple : chaque pod a sa propre IP, et tous les pods peuvent se joindre directement, sur tous les nœuds, sans traduction d'adresse. Ce modèle est mis en œuvre par un plugin CNI (Container Network Interface) : Calico, Cilium, Flannel, ou le VPC CNI d'AWS sur EKS (partie 3).

    Exposer des applications HTTP : Ingress

    Créer un Service LoadBalancer par application coûte cher (un load balancer chacun) et complique la gestion des certificats. Un Ingress décrit des règles de routage HTTP(S) par nom d'hôte et par chemin vers des Services, derrière un point d'entrée commun.

    apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: boutique
spec:
  ingressClassName: alb
  tls:
    - hosts: [shop.example.com]
      secretName: shop-tls
  rules:
    - host: shop.example.com
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend: { service: { name: api, port: { number: 80 } } }
          - path: /
            pathType: Prefix
            backend: { service: { name: web, port: { number: 80 } } }

    Un objet Ingress ne fait rien seul : il faut un contrôleur d'Ingress qui le met en œuvre (AWS Load Balancer Controller, Traefik, HAProxy, NGINX Inc., etc.). cert-manager automatise l'obtention et le renouvellement des certificats TLS (Let's Encrypt, PKI interne).

    Gateway API

    Gateway API est le successeur d'Ingress, stable depuis 2023. Il sépare les responsabilités en plusieurs objets :

    • GatewayClass : le type d'implémentation (géré par l'équipe plateforme) ;
    • Gateway : le point d'entrée, ses ports et certificats (équipe plateforme ou ops) ;
    • HTTPRoute, GRPCRoute… : les règles de routage (équipes applicatives).

    Il gère nativement ce qu'Ingress laissait à des annotations propres à chaque contrôleur : répartition pondérée du trafic (déploiements canary), réécriture d'en-têtes, routage entre namespaces, autres protocoles que HTTP.

    Fin de ingress-nginx Le projet communautaire ingress-nginx, longtemps le contrôleur d'Ingress le plus répandu, a été retiré par le projet Kubernetes en 2026 (plus de correctifs, y compris de sécurité). Pour les nouveaux projets, privilégiez Gateway API ou un contrôleur maintenu ; pour l'existant, planifiez une migration.

    Filtrer le trafic : NetworkPolicy

    Par défaut, tout pod peut parler à tout pod. Une NetworkPolicy restreint les flux entrants (ingress) et sortants (egress) des pods sélectionnés.

    # 1. Tout interdire en entrée dans le namespace
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: default-deny-ingress, namespace: boutique }
spec:
  podSelector: {}
  policyTypes: [Ingress]
---
# 2. Autoriser uniquement web → api sur le port 8080
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: allow-web-to-api, namespace: boutique }
spec:
  podSelector: { matchLabels: { app: api } }
  ingress:
    - from: [ { podSelector: { matchLabels: { app: web } } } ]
      ports: [ { port: 8080 } ]
    Le CNI doit les prendre en charge Les NetworkPolicies sont appliquées par le plugin réseau. Avec un CNI qui ne les gère pas, elles sont acceptées par l'API mais sans aucun effet.

    Points clés

    • Une IP par pod, réseau à plat, mis en œuvre par un plugin CNI.
    • Ingress (ou Gateway API, son successeur) route le HTTP par hôte et chemin ; il faut un contrôleur.
    • Par défaut tout est ouvert : NetworkPolicy « deny all » puis autorisations explicites.

    Le stockage persistant

    Le système de fichiers d'un conteneur disparaît avec lui. Pour conserver des données, on utilise des volumes. Certains sont temporaires (emptyDir, qui vit le temps du pod), d'autres sont persistants.

    PV, PVC et StorageClass

    ObjetRôleQui le crée ?
    PersistentVolumeClaim (PVC)Une demande de stockage : taille, mode d'accès, classeL'équipe applicative
    PersistentVolume (PV)Un volume réel (disque cloud, partage NFS…) rattaché au clusterCréé automatiquement (provisionnement dynamique) ou par un administrateur
    StorageClassUn « type » de stockage et la façon de le créer (driver CSI, performances, chiffrement)L'équipe plateforme
     
    apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data
spec:
  storageClassName: gp3
  accessModes: [ReadWriteOnce]
  resources:
    requests:
      storage: 20Gi

    Avec le provisionnement dynamique, la création du PVC déclenche automatiquement la création du disque par le driver CSI (Container Storage Interface) de la StorageClass.

    Les modes d'accès

    ModeSignificationExemples de stockage
    ReadWriteOnce (RWO)Lecture-écriture par un seul nœud à la foisDisques en mode bloc : Amazon EBS, Azure Disk
    ReadWriteOncePod (RWOP)Lecture-écriture par un seul podIdem, avec garantie plus stricte
    ReadOnlyMany (ROX)Lecture seule par plusieurs nœudsPartages de fichiers
    ReadWriteMany (RWX)Lecture-écriture par plusieurs nœudsSystèmes de fichiers partagés : Amazon EFS, NFS, Azure Files

    Points d'attention

    • reclaimPolicy : avec Delete (souvent la valeur par défaut), supprimer le PVC supprime le disque et ses données. Utilisez Retain pour les données critiques.
    • volumeBindingMode: WaitForFirstConsumer : le disque est créé seulement quand le pod est placé, dans la même zone que lui. Indispensable pour les disques liés à une zone de disponibilité.
    • Avec un StatefulSet, volumeClaimTemplates crée un PVC par pod (data-db-0, data-db-1…), conservé même si le pod est recréé.
    • Un volume persistant n'est pas une sauvegarde : prévoyez des snapshots (VolumeSnapshot) ou un outil comme Velero.
    • Pour les bases de données en production, un service managé (RDS, Cloud SQL…) est souvent plus simple à opérer que leur hébergement dans le cluster.

    Points clés

    • PVC = demande, PV = volume réel, StorageClass = type et méthode de création (CSI).
    • RWO = un nœud (disques bloc) ; RWX = plusieurs nœuds (systèmes de fichiers partagés).
    • Attention à reclaimPolicy: Delete ; un volume n'est pas une sauvegarde.
    Module 5

    Sécuriser un cluster

    Authentification et autorisation

    Chaque requête à l'API server passe par trois étapes : authentification (qui êtes-vous ?), autorisation (avez-vous le droit ?) et admission (la requête respecte-t-elle les règles du cluster ?).

    • Les utilisateurs humains ne sont pas des objets Kubernetes : ils viennent d'un fournisseur d'identité externe (OIDC, IAM sur EKS…).
    • Les applications utilisent des ServiceAccounts : chaque pod s'exécute sous un ServiceAccount, dont le jeton lui permet d'appeler l'API.

    RBAC

    ObjetPortéeRôle
    RoleUn namespaceListe de permissions : verbes (get, list, create…) sur des ressources
    ClusterRoleTout le clusterIdem, pour des ressources globales ou tous les namespaces
    RoleBindingUn namespaceAttribue un Role (ou un ClusterRole) à des utilisateurs, groupes ou ServiceAccounts, dans ce namespace
    ClusterRoleBindingTout le clusterAttribue un ClusterRole sur tout le cluster
     
    # Vérifier un droit
kubectl auth can-i delete pods -n boutique --as alice@example.com

    Le RBAC n'accorde que des permissions : tout ce qui n'est pas autorisé est interdit. Appliquez le moindre privilège ; méfiez-vous des droits *, de l'accès aux Secrets, de pods/exec et du droit de créer des pods (qui permet souvent d'obtenir les droits d'autres ServiceAccounts).

    Durcir les pods

    Les Pod Security Standards définissent trois niveaux : privileged (aucune restriction), baseline (bloque les élévations de privilèges connues) et restricted (bonnes pratiques de durcissement). Le contrôleur intégré Pod Security Admission les applique par namespace, via un label :

    kubectl label namespace boutique pod-security.kubernetes.io/enforce=restricted

    Un pod conforme au niveau restricted ressemble à ceci :

        securityContext:
      runAsNonRoot: true
      allowPrivilegeEscalation: false
      readOnlyRootFilesystem: true
      capabilities: { drop: [ALL] }
      seccompProfile: { type: RuntimeDefault }

    Pour des règles plus fines (registres autorisés, labels obligatoires, interdiction de latest), on utilise un moteur de politiques : Kyverno, OPA Gatekeeper, ou les ValidatingAdmissionPolicies natives.

    Chaîne d'approvisionnement et exécution

    • Images minimales (distroless, Alpine), scannées (Trivy, Grype), signées (Sigstore / cosign), issues de registres maîtrisés.
    • Secrets : chiffrement d'etcd et coffre-fort externe (voir partie 1).
    • Accès à l'API : endpoint privé ou restreint, journaux d'audit activés.
    • Détection à l'exécution : Falco, GuardDuty sur EKS, ou les fonctions de sécurité de votre plateforme d'observabilité.
    • Mises à jour régulières de Kubernetes et des nœuds.

    Points clés

    • Requête API : authentification → autorisation (RBAC) → admission.
    • RBAC : Role/ClusterRole + RoleBinding/ClusterRoleBinding, moindre privilège.
    • Pod Security Standards (restricted si possible) via des labels de namespace.
    • Images scannées et signées, secrets externalisés, audit, détection à l'exécution.

    L'autoscaling

    Kubernetes peut adapter automatiquement la capacité à la charge, à deux niveaux : les pods et les nœuds.

    OutilCe qu'il ajusteDéclencheur
    HPA (Horizontal Pod Autoscaler)Le nombre de réplicasCPU, mémoire, métriques personnalisées ou externes
    VPA (Vertical Pod Autoscaler)Les requests / limits des podsConsommation observée dans le temps
    KEDALe nombre de réplicas, jusqu'à zéroÉvénements : longueur d'une file SQS ou Kafka, requêtes, planning…
    Cluster AutoscalerLe nombre de nœuds d'un groupe de nœudsPods en attente (Pending) faute de place, nœuds sous-utilisés
    KarpenterLes nœuds, en choisissant le type d'instance adaptéPods en attente ; consolidation des nœuds sous-utilisés
     
    apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: api }
  minReplicas: 3
  maxReplicas: 20
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: { type: Utilization, averageUtilization: 70 }   # % des requests

    Comment les niveaux s'enchaînent

    1. La charge augmente : le HPA passe de 3 à 8 réplicas.
    2. Les nouveaux pods ne trouvent pas de place : ils restent Pending.
    3. Le Cluster Autoscaler ou Karpenter voit ces pods et ajoute des nœuds.
    4. La charge baisse : le HPA réduit les réplicas, puis les nœuds vides ou sous-utilisés sont retirés.
    Conditions pour que ça marche
    • Le HPA en pourcentage de CPU se calcule par rapport aux requests : sans requests, il ne fonctionne pas.
    • Le HPA sur les ressources a besoin de metrics-server (ou d'une autre source de métriques).
    • Ne pilotez pas le même Deployment avec le HPA et le VPA sur la même métrique (CPU ou mémoire) : ils se contredisent.
    • Des PDB et un arrêt propre sont nécessaires pour que la réduction ne provoque pas d'erreurs.

    Points clés

    • HPA : nombre de pods ; VPA : taille des pods ; KEDA : événements, jusqu'à zéro.
    • Cluster Autoscaler ou Karpenter : nombre de nœuds, déclenché par les pods Pending.
    • Requests correctes et metrics-server indispensables.
    Module 7

    Packaging et déploiement continu

    Helm

    Helm est le gestionnaire de paquets de Kubernetes. Un chart regroupe des modèles de manifestes et un fichier values.yaml de paramètres ; chaque installation est une release versionnée.

    helm repo add bitnami https://charts.bitnami.com/bitnami
helm install cache bitnami/redis -n cache --create-namespace -f values-prod.yaml
helm upgrade cache bitnami/redis -n cache -f values-prod.yaml
helm rollback cache 1
helm template ...        # afficher les manifestes générés sans rien installer

    Helm est idéal pour installer des logiciels tiers (bases, outils, opérateurs) et pour distribuer des applications paramétrables. Les charts peuvent aussi être stockés dans des registres OCI.

    Kustomize

    Kustomize, intégré à kubectl (kubectl apply -k), part de manifestes YAML ordinaires (base) et applique des surcharges par environnement (overlays), sans langage de templates.

    app/
├── base/                 # deployment.yaml, service.yaml, kustomization.yaml
└── overlays/
    ├── dev/              # 1 réplica, image de dev
    └── prod/             # 3 réplicas, ressources plus élevées

    GitOps

    Le GitOps fait de Git la source de vérité de ce qui tourne dans le cluster. Un agent installé dans le cluster (Argo CD ou Flux) :

    • tire (pull) les manifestes depuis Git et les applique ;
    • détecte la dérive (une modification manuelle) et la corrige ou la signale ;
    • rend tout changement traçable : un déploiement = un commit, un retour arrière = un git revert.
    Pourquoi le mode pull ? La CI n'a plus besoin d'identifiants d'administration du cluster : c'est le cluster qui va chercher sa configuration. Le pipeline CI construit, teste et publie l'image, puis met à jour le tag dans le dépôt de configuration ; Argo CD ou Flux s'occupent du reste.

    Stratégies de déploiement avancées

    • Blue/green : deux versions complètes en parallèle, bascule instantanée du trafic.
    • Canary : une petite part du trafic (5 %, puis 25 %…) va vers la nouvelle version, avec analyse automatique des métriques.
    • Outils : Argo Rollouts, Flagger, ou la répartition pondérée de Gateway API.

    Points clés

    • Helm : charts paramétrables, releases, idéal pour les logiciels tiers.
    • Kustomize : base + overlays, sans templates, intégré à kubectl.
    • GitOps (Argo CD, Flux) : Git comme source de vérité, mode pull, correction de la dérive.
    Module 8

    Observabilité et dépannage

    Que surveiller ?

    📊 Métriques

    metrics-server pour kubectl top et le HPA ; Prometheus (avec kube-state-metrics et node-exporter) ou une plateforme comme Dynatrace pour l'historique et les alertes.

    📜 Logs

    Les conteneurs écrivent sur la sortie standard ; un agent en DaemonSet (Fluent Bit, OpenTelemetry Collector…) les collecte et les envoie vers un backend centralisé.

    🔗 Traces

    Instrumentation OpenTelemetry ou agent automatique, pour suivre les requêtes entre services.

    📣 Événements

    Les événements Kubernetes (échecs de placement, redémarrages, évictions) ne sont conservés qu'environ une heure : exportez-les.

    Les signaux essentiels à alerter : redémarrages de conteneurs, pods non prêts, pods Pending prolongés, OOMKilled, saturation CPU/mémoire des nœuds, nœuds NotReady, échecs de déploiement, expiration des certificats.

    Méthode de dépannage

    1. Où ? kubectl get pods -A : quels pods sont en erreur, dans quel namespace, sur quel nœud ?
    2. Pourquoi ? kubectl describe pod : lisez les événements en bas de la sortie.
    3. Que dit l'application ? kubectl logs (et --previous après un plantage).
    4. Le réseau ? Le Service a-t-il des endpoints ? (kubectl get endpointslices -l kubernetes.io/service-name=web) Les labels du sélecteur correspondent-ils à ceux des pods ? Une NetworkPolicy bloque-t-elle ?
    5. Le nœud ? kubectl describe node : pression mémoire ou disque, capacité allouée.
    6. Aller dans le pod : kubectl exec, ou kubectl debug pour ajouter un conteneur de diagnostic à un pod dont l'image ne contient pas d'outils.

    Diagnostic des cas fréquents

    SymptômePistes
    PendingRequests trop élevées, aucun nœud compatible (taints, affinity), quota atteint, PVC non lié, autoscaler de nœuds absent ou bloqué
    ImagePullBackOffNom ou tag faux, registre privé sans imagePullSecrets ou sans droits, limite de téléchargement du registre
    CrashLoopBackOffErreur au démarrage (configuration, variable manquante, dépendance absente), liveness trop agressive
    OOMKilledLimit mémoire trop basse ou fuite mémoire
    Service qui ne répond pasAucun pod prêt, sélecteur qui ne correspond pas, mauvais targetPort, NetworkPolicy
    EvictedLe nœud manquait de mémoire ou de disque ; vérifiez les requests et l'espace disque (logs, images)

    Points clés

    • Métriques, logs, traces et événements : les événements Kubernetes sont éphémères, exportez-les.
    • Réflexes : get → describe (événements) → logs → réseau → nœud.
    • kubectl debug pour diagnostiquer des images sans outils.
