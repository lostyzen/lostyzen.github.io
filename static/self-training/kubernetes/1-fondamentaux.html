    Module 1

    Des conteneurs à l'orchestration

    Le conteneur

    Un conteneur embarque une application avec tout ce dont elle a besoin pour tourner (bibliothèques, runtime, configuration par défaut), et l'exécute de façon isolée sur un système hôte. Contrairement à une machine virtuelle, il partage le noyau du système hôte : il démarre en quelques secondes et consomme beaucoup moins de ressources.

    Machine virtuelleConteneur
    IsolationSystème d'exploitation complet, hyperviseurProcessus isolés (namespaces et cgroups Linux), noyau partagé
    TaillePlusieurs GoQuelques dizaines à centaines de Mo
    DémarrageMinutesSecondes
    • Une image est le modèle immuable à partir duquel on lance des conteneurs. Elle est construite (par exemple avec un Dockerfile) et versionnée par un tag (monapp:2.3.1).
    • Les images sont stockées dans un registre : Docker Hub, GitHub Container Registry, Amazon ECR, Harbor…
    • Le format des images et des runtimes est standardisé par l'OCI (Open Container Initiative) : une image construite avec Docker tourne avec containerd ou CRI-O.

    Pourquoi un orchestrateur ?

    Lancer un conteneur sur une machine est simple. En faire tourner des centaines, sur des dizaines de machines, en production, soulève d'autres questions :

    📍 Placement

    Sur quelle machine démarrer chaque conteneur, selon les ressources disponibles ?

    ❤️ Auto-réparation

    Que se passe-t-il quand un conteneur plante ou qu'une machine tombe ?

    📈 Mise à l'échelle

    Comment passer de 3 à 30 instances quand la charge augmente ?

    🔀 Réseau

    Comment les services se trouvent-ils et répartissent-ils la charge entre leurs instances ?

    🚀 Déploiements

    Comment livrer une nouvelle version sans interruption, et revenir en arrière ?

    🔐 Configuration

    Comment injecter configuration et secrets selon l'environnement ?

    Kubernetes (souvent abrégé K8s) répond à ces questions. Issu de l'expérience de Google avec son système interne Borg, il a été rendu open source en 2014 et confié à la CNCF (Cloud Native Computing Foundation). C'est aujourd'hui le standard de fait de l'orchestration de conteneurs.

    Le modèle déclaratif et la boucle de réconciliation

    Comme Terraform ou Ansible, Kubernetes est déclaratif : on ne lui dit pas « démarre 3 conteneurs », on lui déclare « je veux 3 réplicas de cette application ». Kubernetes enregistre cet état désiré, puis des contrôleurs comparent en permanence l'état désiré à l'état réel et agissent pour réduire l'écart.

    Exemple Vous demandez 3 réplicas. Une machine tombe et emporte un réplica : l'état réel passe à 2. Le contrôleur le constate et recrée immédiatement un réplica sur une autre machine. Personne n'a eu besoin d'intervenir.

    Points clés

    • Conteneur = application isolée qui partage le noyau de l'hôte ; image = modèle immuable versionné.
    • Kubernetes orchestre : placement, auto-réparation, mise à l'échelle, réseau, déploiements.
    • Modèle déclaratif : on décrit l'état désiré, les contrôleurs réconcilient en continu.
    Module 2

    L'architecture d'un cluster

    Un cluster Kubernetes se compose d'un plan de contrôle (control plane), qui prend les décisions, et de nœuds de travail (worker nodes), qui exécutent les applications.

    Le plan de contrôle

    ComposantRôle
    kube-apiserverLe point d'entrée unique. Tous les échanges passent par lui : kubectl, contrôleurs, kubelets. Il authentifie, autorise, valide les objets et les enregistre dans etcd.
    etcdBase de données clé-valeur distribuée qui contient tout l'état du cluster. Sa sauvegarde est vitale sur un cluster autogéré.
    kube-schedulerChoisit le nœud sur lequel placer chaque nouveau pod, selon les ressources demandées et les contraintes de placement.
    kube-controller-managerExécute les contrôleurs (Deployment, ReplicaSet, Node, Job…) qui réconcilient l'état réel avec l'état désiré.
    cloud-controller-managerFait le lien avec le fournisseur cloud : load balancers, routes, informations sur les machines.

    En production, le plan de contrôle est redondé (au moins 3 instances d'etcd). Avec un service managé comme EKS, AKS ou GKE, c'est le fournisseur cloud qui l'opère (voir partie 3).

    Les nœuds

    • kubelet : l'agent de chaque nœud. Il reçoit les pods qui lui sont attribués, demande au runtime de démarrer les conteneurs, surveille leur santé et remonte leur statut à l'API.
    • Runtime de conteneurs : containerd ou CRI-O, via l'interface standard CRI. Docker Engine n'est plus utilisé directement par Kubernetes depuis la version 1.24, mais les images construites avec Docker fonctionnent toujours.
    • kube-proxy : met en œuvre les Services sur chaque nœud (règles iptables ou IPVS). Certains plugins réseau, comme Cilium, peuvent le remplacer.

    Ce qui se passe lors d'un déploiement

    1. kubectl apply envoie le manifeste à l'API server, qui le valide et l'enregistre dans etcd.
    2. Le contrôleur de Deployment voit le nouvel objet et crée un ReplicaSet, dont le contrôleur crée les pods demandés.
    3. Le scheduler voit des pods sans nœud attribué et choisit un nœud pour chacun.
    4. Le kubelet du nœud choisi voit le pod qui lui est attribué et demande au runtime de télécharger l'image et de démarrer les conteneurs.
    Tout passe par l'API Les composants ne se parlent pas directement : ils observent l'API server (mécanisme de watch) et y écrivent leurs résultats. C'est ce qui rend Kubernetes extensible : un nouveau contrôleur peut s'ajouter sans modifier les autres.

    Points clés

    • Plan de contrôle : API server, etcd, scheduler, controller manager.
    • Nœuds : kubelet, runtime de conteneurs (containerd), kube-proxy.
    • L'API server est le point d'entrée unique ; etcd contient tout l'état.
    Module 3

    Pods et workloads

    Le Pod

    Le Pod est la plus petite unité déployable de Kubernetes. Il contient un ou plusieurs conteneurs qui partagent :

    • la même adresse IP et les mêmes ports (ils communiquent via localhost) ;
    • des volumes communs ;
    • le même cycle de vie et le même nœud.

    Le cas le plus courant est un pod = un conteneur. On ajoute un conteneur supplémentaire pour un besoin étroitement lié :

    • Init containers : s'exécutent jusqu'au bout avant les conteneurs principaux (attendre une base de données, préparer des fichiers).
    • Sidecars : tournent à côté du conteneur principal (proxy de service mesh, collecteur de logs). Kubernetes les gère nativement sous forme d'init containers avec restartPolicy: Always.
    Les pods sont éphémères Un pod n'est jamais « réparé » : s'il meurt ou si son nœud tombe, un nouveau pod est créé, avec une nouvelle IP. On ne crée donc presque jamais de pod directement : on passe par un contrôleur (Deployment, StatefulSet…) qui les recrée.

    Les contrôleurs de workloads

    ObjetUsageExemple
    DeploymentApplications sans état : réplicas interchangeables, mises à jour progressives, retour arrièreAPI REST, front-end web
    StatefulSetApplications avec état : identité stable (db-0, db-1), ordre de démarrage, un volume persistant par podBases de données, Kafka, Elasticsearch
    DaemonSetExactement un pod par nœud (ou par nœud sélectionné)Agent de logs, agent de supervision, plugin réseau
    JobTâche qui s'exécute jusqu'à son terme, avec relance en cas d'échecMigration de base, traitement par lot
    CronJobJob lancé selon une planification (syntaxe cron)Sauvegarde nocturne, purge

    Un Deployment ne gère pas directement les pods : il gère des ReplicaSets, qui maintiennent le nombre de pods voulu. À chaque nouvelle version, le Deployment crée un nouveau ReplicaSet et fait basculer progressivement les pods de l'ancien vers le nouveau.

    apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  labels:
    app: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web              # les pods gérés par ce Deployment
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1           # au plus 1 pod en plus pendant la mise à jour
      maxUnavailable: 0     # jamais moins de 3 pods disponibles
  template:                 # modèle des pods
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: ghcr.io/acme/web:2.3.1
          ports:
            - containerPort: 8080

    Mises à jour et retour arrière

    • RollingUpdate (par défaut) : remplace les pods progressivement, selon maxSurge et maxUnavailable (25 % chacun par défaut). Pas d'interruption si l'application est bien configurée.
    • Recreate : arrête tous les anciens pods avant de démarrer les nouveaux. Il y a une interruption, mais jamais deux versions en même temps.
    • kubectl rollout status deployment/web suit le déploiement ; kubectl rollout undo deployment/web revient à la version précédente.
    Évitez le tag latest Avec image: web:latest, on ne sait pas quelle version tourne, et un retour arrière n'a pas de sens. Utilisez un tag précis (2.3.1), voire une empreinte (@sha256:…).

    Points clés

    • Pod = un ou plusieurs conteneurs partageant IP, volumes et cycle de vie ; il est éphémère.
    • Deployment pour le sans-état, StatefulSet pour l'avec-état, DaemonSet pour un pod par nœud, Job/CronJob pour les tâches.
    • Deployment → ReplicaSet → Pods ; RollingUpdate par défaut, rollout undo pour revenir en arrière.
    Module 4

    Labels, Services et découverte de services

    Labels et sélecteurs

    Les labels sont des paires clé-valeur attachées aux objets (app: web, tier: frontend, env: prod). Les sélecteurs permettent de désigner un ensemble d'objets par leurs labels. C'est le mécanisme qui relie les objets entre eux : un Deployment trouve ses pods, un Service trouve ses pods de destination, par label.

    kubectl get pods -l app=web,env=prod

    Les annotations, elles, servent à stocker des métadonnées non utilisées pour la sélection (informations de build, configuration d'outils tiers).

    Le Service

    Les pods vont et viennent, et leurs IP changent. Un Service fournit un point d'accès stable (une IP virtuelle et un nom DNS) devant un ensemble de pods sélectionnés par label, et répartit la charge entre eux.

    apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  type: ClusterIP
  selector:
    app: web          # envoie le trafic aux pods portant ce label
  ports:
    - port: 80        # port du Service
      targetPort: 8080  # port du conteneur

    Seuls les pods prêts (ready, voir les sondes en partie 2) reçoivent du trafic. La liste à jour des pods derrière un Service est tenue dans des objets EndpointSlice.

    Les types de Service

    TypeAccessible depuisUsage
    ClusterIP (défaut)L'intérieur du cluster uniquementCommunication entre services internes
    NodePortChaque nœud, sur un port fixe (30000–32767 par défaut)Tests, intégration avec un load balancer externe
    LoadBalancerL'extérieur, via un load balancer créé chez le fournisseur cloudExposer un service sur Internet ou sur le réseau d'entreprise
    ExternalNameAlias DNS (CNAME) vers un nom externePointer vers une base de données managée hors du cluster

    Un Service headless (clusterIP: None) ne fait pas de répartition : le DNS renvoie directement les IP des pods. Il est utilisé avec les StatefulSets pour joindre un pod précis (db-0.db).

    Pour exposer des applications HTTP, on préfère en général un seul point d'entrée qui route selon le nom de domaine et le chemin : c'est le rôle d'Ingress et de Gateway API, vus en partie 2.

    La découverte par DNS

    Le cluster embarque un DNS interne (CoreDNS). Chaque Service reçoit un nom de la forme :

    <service>.<namespace>.svc.cluster.local

# Depuis le même namespace, le nom court suffit :
curl http://web
# Depuis un autre namespace :
curl http://web.boutique

    Points clés

    • Labels + sélecteurs relient les objets entre eux.
    • Service = IP et nom DNS stables devant des pods éphémères, avec répartition de charge.
    • ClusterIP (interne), NodePort, LoadBalancer (externe), ExternalName (alias).
    • DNS : service.namespace.svc.cluster.local.
    Module 5

    Configuration, secrets et namespaces

    Une bonne pratique (issue des 12-factor apps) consiste à séparer la configuration du code : la même image est déployée partout, seule la configuration change selon l'environnement.

    ConfigMap

    Un ConfigMap stocke de la configuration non sensible : paires clé-valeur ou fichiers entiers.

    apiVersion: v1
kind: ConfigMap
metadata:
  name: web-config
data:
  LOG_LEVEL: "info"
  app.properties: |
    feature.newCheckout=true
    cache.ttl=300

    On l'injecte dans un pod de deux façons :

    • en variables d'environnement (env / envFrom) : lues au démarrage, un changement demande un redémarrage du pod ;
    • en fichiers via un volume : le contenu est mis à jour dans le pod après un court délai (l'application doit savoir le relire).

    Secret

    Un Secret a la même structure, mais pour les données sensibles : mots de passe, jetons, certificats TLS, identifiants de registre.

    base64 n'est pas du chiffrement Les valeurs d'un Secret sont simplement encodées en base64, ce qui se décode instantanément. Par défaut, elles sont aussi stockées en clair dans etcd. Pour protéger réellement les secrets :
    • activer le chiffrement au repos d'etcd, idéalement avec un KMS ;
    • limiter l'accès aux Secrets par RBAC (partie 2) ;
    • ne jamais commiter de Secret en clair dans Git : utiliser un coffre-fort externe avec External Secrets Operator ou le Secrets Store CSI Driver, ou chiffrer avec Sealed Secrets ou SOPS.

    Namespaces

    Un namespace est un espace de noms qui découpe un cluster en zones logiques : par équipe, par application ou par environnement.

    • Les noms doivent être uniques dans un namespace, pas entre namespaces.
    • Ils servent de périmètre aux droits (RBAC), aux quotas de ressources et aux règles réseau.
    • Namespaces présents par défaut : default, kube-system (composants du cluster), kube-public, kube-node-lease.
    • Certains objets sont globaux au cluster et n'appartiennent à aucun namespace : Node, PersistentVolume, StorageClass, ClusterRole, Namespace lui-même.
    Un namespace n'est pas une barrière de sécurité à lui seul Par défaut, un pod peut joindre n'importe quel pod d'un autre namespace. L'isolation réelle demande des NetworkPolicies, du RBAC et des quotas (partie 2). Pour isoler des clients ou des environnements sensibles, on utilise souvent des clusters distincts.

    Points clés

    • ConfigMap pour la configuration, Secret pour le sensible ; injection par variables ou fichiers.
    • Les Secrets sont seulement encodés en base64 : chiffrement d'etcd, RBAC et coffre-fort externe nécessaires.
    • Namespace = découpage logique, périmètre des droits, quotas et règles réseau.
    Module 6

    Manifestes YAML et kubectl

    La structure d'un manifeste

    Tout objet Kubernetes se décrit avec les mêmes champs de premier niveau :

    ChampContenu
    apiVersionGroupe et version de l'API : v1, apps/v1, batch/v1, networking.k8s.io/v1…
    kindType d'objet : Pod, Deployment, Service…
    metadataNom, namespace, labels, annotations
    specL'état désiré, écrit par vous
    statusL'état observé, écrit par Kubernetes (on ne le renseigne jamais)

    Plusieurs objets peuvent être réunis dans un même fichier, séparés par ---. kubectl explain deployment.spec.strategy documente n'importe quel champ.

    Impératif ou déclaratif

    • Impératif : kubectl create deployment web --image=…, kubectl scale, kubectl edit. Pratique pour tester, mais rien n'est versionné.
    • Déclaratif : kubectl apply -f manifests/. Les manifestes sont dans Git, relus en merge request, et apply peut être relancé autant de fois que nécessaire. C'est la pratique à suivre, et la base du GitOps (partie 2).

    kubectl diff -f manifests/ montre ce qu'un apply changerait, à la manière d'un terraform plan.

    Les commandes essentielles

    CommandeUsage
    kubectl get pods -n boutique -o wideLister des objets (avec nœud et IP)
    kubectl describe pod web-7d9f…Détails d'un objet et événements récents : la première commande de dépannage
    kubectl logs web-7d9f… [-c conteneur] [--previous]Logs d'un conteneur ; --previous pour l'instance qui vient de planter
    kubectl exec -it web-7d9f… -- shOuvrir un shell dans un conteneur
    kubectl port-forward svc/web 8080:80Accéder en local à un service du cluster
    kubectl get events --sort-by=.lastTimestampÉvénements récents du namespace
    kubectl config get-contexts / use-contextLister et changer de cluster (fichier ~/.kube/config)
    Vérifiez toujours votre contexte Le fichier kubeconfig peut contenir plusieurs clusters. Une commande lancée sur le mauvais contexte peut supprimer des ressources en production. Affichez le contexte courant dans votre invite de commande, et utilisez des outils comme kubectx / kubens.

    Les statuts de pod à connaître

    StatutCause probable
    PendingAucun nœud ne peut accueillir le pod (ressources insuffisantes, contraintes de placement) ou volume non disponible
    ImagePullBackOff / ErrImagePullImage introuvable (nom ou tag erroné) ou registre privé sans identifiants
    CrashLoopBackOffLe conteneur démarre puis s'arrête en boucle : regardez kubectl logs --previous
    OOMKilledLe conteneur a dépassé sa limite mémoire (code de sortie 137)
    Running mais pas ReadyLa sonde de disponibilité (readiness) échoue : le pod ne reçoit pas de trafic

    Points clés

    • Manifeste = apiVersion, kind, metadata, spec ; status est rempli par Kubernetes.
    • Déclaratif avec kubectl apply et des manifestes dans Git.
    • describe et logs sont les premiers réflexes de dépannage.
    • Vérifiez toujours le contexte kubectl avant d'agir.
