    Module 1

    Présentation et architecture d'EKS

    Amazon EKS fournit un plan de contrôle Kubernetes managé, conforme à la version open source (certifié CNCF) : les manifestes, Helm, kubectl et les outils de l'écosystème fonctionnent comme sur n'importe quel cluster.

    La responsabilité partagée

    AWS prend en chargeVous restez responsable de
    Le plan de contrôle : API servers et etcd répartis sur plusieurs zones de disponibilité, haute disponibilité, sauvegarde, correctifsLes nœuds (sauf avec Fargate ou Auto Mode) : choix, mises à jour, correctifs du système
    La disponibilité de l'API Kubernetes (avec un engagement de niveau de service)Les mises à jour de version du cluster : vous les déclenchez
    L'intégration avec IAM, le VPC, les load balancers, CloudWatchLes applications, leur configuration, le RBAC, les NetworkPolicies, les add-ons

    Le plan de contrôle tourne dans un compte AWS géré par EKS. Il communique avec vos nœuds via des interfaces réseau (ENI) qu'EKS crée dans les sous-réseaux de votre VPC. L'endpoint de l'API peut être public (restreignez alors les plages d'IP autorisées), privé (accessible seulement depuis le VPC), ou les deux.

    Versions et support

    • Kubernetes publie environ trois versions mineures par an.
    • Sur EKS, chaque version bénéficie de 14 mois de support standard, puis de 12 mois de support étendu, facturé plus cher.
    • À la fin du support étendu, AWS met automatiquement le cluster à jour.
    Coût du support étendu Le plan de contrôle coûte environ 0,10 $ par heure en support standard, et environ 0,60 $ par heure en support étendu. Une version non mise à jour multiplie donc le coût du plan de contrôle par six : planifiez les mises à jour (module 6).

    Points clés

    • EKS = plan de contrôle managé, multi-AZ, conforme à Kubernetes open source.
    • Vous restez responsable des nœuds (selon l'option), des mises à jour, des applications et des droits.
    • 14 mois de support standard + 12 mois de support étendu, plus cher.

    Les options de calcul (data plane)

    OptionPrincipePoints fortsLimites
    Groupes de nœuds managés (managed node groups)EKS crée et gère des groupes Auto Scaling d'instances EC2 avec des AMI optimiséesMises à jour des nœuds facilitées (remplacement progressif avec drain)Un type d'instance par groupe (ou une liste restreinte) ; mise à l'échelle par groupe
    Nœuds autogérésVous gérez vous-même vos groupes Auto Scaling et vos AMIContrôle totalToute la charge d'exploitation est pour vous
    FargateChaque pod tourne dans sa propre micro-VM, sans nœud visibleAucun serveur à gérer, isolation fortePas de DaemonSet, pas de pods privilégiés, pas de volumes EBS ; démarrage plus lent ; coût plus élevé à grande échelle
    KarpenterAutoscaler de nœuds open source qui crée directement les instances EC2 adaptées aux pods en attenteChoix de l'instance au plus juste, Spot, consolidation, rapiditéComposant à installer et à opérer (sauf avec Auto Mode)
    EKS Auto ModeAWS gère les nœuds (basés sur Karpenter) et les composants essentiels : réseau, load balancers, stockage blocExpérience proche du « serverless » avec la souplesse d'EC2Surcoût par instance ; moins de personnalisation des nœuds

    Karpenter en pratique

    Karpenter ne raisonne pas en groupes de nœuds fixes. On décrit des contraintes, et il choisit l'instance la moins chère qui convient aux pods en attente :

    apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: default
spec:
  template:
    spec:
      requirements:
        - key: karpenter.sh/capacity-type
          operator: In
          values: [spot, on-demand]          # Spot en priorité si disponible
        - key: kubernetes.io/arch
          operator: In
          values: [arm64, amd64]             # Graviton autorisé
      nodeClassRef:                          # EC2NodeClass : AMI, sous-réseaux, groupes de sécurité
        group: karpenter.k8s.aws
        kind: EC2NodeClass
        name: default
  disruption:
    consolidationPolicy: WhenEmptyOrUnderutilized   # regroupe les pods pour libérer des nœuds
  limits:
    cpu: 1000

    Réduire les coûts de calcul

    • Instances Spot : jusqu'à environ 90 % moins chères, mais récupérables par AWS avec un préavis de 2 minutes. Elles conviennent aux charges sans état, tolérantes aux interruptions et réparties sur plusieurs réplicas.
    • Graviton (processeurs ARM d'AWS) : meilleur rapport prix/performance, à condition de construire des images multi-architectures.
    • Consolidation (Karpenter) et requests bien dimensionnées : moins de capacité réservée inutilement.
    • Savings Plans pour la base de charge stable.

    Points clés

    • Groupes de nœuds managés : simples et éprouvés. Fargate : pas de nœuds, mais des limites.
    • Karpenter : instances choisies au plus juste, Spot, consolidation.
    • EKS Auto Mode : AWS gère les nœuds et les composants essentiels.
    • Spot, Graviton et requests justes sont les principaux leviers de coût.
    Module 3

    Le réseau sur EKS

    Le VPC CNI : des pods avec des IP du VPC

    Sur EKS, le plugin réseau par défaut est l'Amazon VPC CNI. Chaque pod reçoit une vraie adresse IP du VPC, prise sur les interfaces réseau (ENI) du nœud.

    • Avantage : pas de réseau superposé (overlay). Les pods sont directement joignables depuis le VPC, les load balancers peuvent cibler les pods, et les outils réseau AWS (VPC Flow Logs, groupes de sécurité) s'appliquent.
    • Contrainte n° 1 : la consommation d'IP. Chaque pod consomme une IP du sous-réseau. Un cluster dense dans des sous-réseaux trop petits (/24 = 251 adresses utilisables) épuise vite les adresses : de nouveaux pods ne peuvent plus démarrer.
    • Contrainte n° 2 : le nombre de pods par nœud dépend du type d'instance. Sans option particulière : ENI × (IP par ENI − 1) + 2. Par exemple, une m5.large (3 ENI × 10 IP) accepte 29 pods.

    Les solutions à l'épuisement des IP

    SolutionPrincipe
    Prévoir largeDes sous-réseaux dédiés aux pods, en /19 ou plus, dès la conception du VPC
    Prefix delegationLe CNI attribue des préfixes /28 (16 adresses) au lieu d'adresses individuelles : beaucoup plus de pods par nœud (instances Nitro)
    Custom networkingLes pods prennent leurs IP dans un bloc CIDR secondaire, souvent dans la plage 100.64.0.0/10, distinct des sous-réseaux des nœuds
    IPv6Cluster en IPv6 : plus de problème de nombre d'adresses pour les pods

    Le VPC CNI permet aussi d'appliquer des groupes de sécurité aux pods (et pas seulement aux nœuds), par exemple pour n'autoriser l'accès à une base RDS qu'à certains pods. Il prend aussi en charge les NetworkPolicies Kubernetes, à activer explicitement.

    Exposer des applications : AWS Load Balancer Controller

    L'AWS Load Balancer Controller (inclus dans EKS Auto Mode, à installer sinon) crée les load balancers AWS à partir des objets Kubernetes :

    Objet KubernetesLoad balancer crééUsage
    Ingress (ou Gateway API)ALB (Application Load Balancer, couche 7)HTTP/HTTPS : routage par hôte et chemin, certificats ACM, WAF
    Service type LoadBalancerNLB (Network Load Balancer, couche 4)TCP/UDP, hautes performances, IP fixes
     
    metadata:
  annotations:
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip      # le trafic va directement aux IP des pods
    alb.ingress.kubernetes.io/listen-ports: '[{"HTTP": 80}, {"HTTPS": 443}]'
    alb.ingress.kubernetes.io/ssl-redirect: "443"      # redirige HTTP vers HTTPS
    alb.ingress.kubernetes.io/certificate-arn: arn:aws:acm:eu-west-3:123456789012:certificate/…   # certificat ACM
spec:
  ingressClassName: alb

    Le mode target-type: ip envoie le trafic directement aux pods, ce qui est possible grâce aux IP du VPC. Le mode instance passe par un NodePort sur les nœuds. Plusieurs Ingress peuvent partager un même ALB grâce à l'annotation group.name, ce qui réduit les coûts.

    Points clés

    • VPC CNI : chaque pod a une IP du VPC ; attention à l'épuisement des adresses.
    • Remèdes : grands sous-réseaux, prefix delegation, custom networking, IPv6.
    • AWS Load Balancer Controller : Ingress → ALB, Service LoadBalancer → NLB.
    Module 4

    Identité et accès : IAM et Kubernetes

    Sur EKS, deux questions d'identité distinctes se posent :

    1. Qui peut accéder au cluster ? Des identités IAM (utilisateurs, rôles SSO, pipelines CI) qui doivent obtenir des droits Kubernetes.
    2. Que peuvent faire les pods dans AWS ? Des applications qui doivent lire un bucket S3, écrire dans DynamoDB, lire un secret…

    1. Accès au cluster : access entries

    L'authentification se fait avec IAM : aws eks update-kubeconfig configure kubectl pour obtenir un jeton à partir de vos identifiants AWS. Il faut ensuite associer l'identité IAM à des droits Kubernetes :

    MéthodePrincipeStatut
    Access entriesAssociations gérées par l'API EKS (console, CLI, Terraform) entre un rôle IAM et des droits : access policies prédéfinies (par exemple AmazonEKSClusterAdminPolicy, AmazonEKSViewPolicy) ou groupes Kubernetes liés à votre RBACRecommandée
    ConfigMap aws-authCorrespondances IAM → utilisateurs/groupes Kubernetes, stockées dans un ConfigMap du namespace kube-systemDépréciée : une erreur de syntaxe pouvait bloquer tout accès au cluster

    Le mode d'authentification du cluster (API, API_AND_CONFIG_MAP ou CONFIG_MAP) indique quelle méthode est active ; API_AND_CONFIG_MAP sert pendant la migration.

    Bonne pratique Accordez les droits à des rôles IAM (rôles SSO par équipe, rôle de la CI), jamais à des utilisateurs IAM individuels. Limitez les administrateurs du cluster et préférez des droits limités à des namespaces.

    2. Droits AWS des pods : Pod Identity et IRSA

    À éviter : le rôle du nœud Si l'on ajoute des permissions au rôle IAM des nœuds EC2, tous les pods du nœud en héritent. Chaque application doit avoir son propre rôle, avec le moindre privilège.
    EKS Pod IdentityIRSA (IAM Roles for Service Accounts)
    PrincipeUne association (cluster, namespace, ServiceAccount → rôle IAM) créée par l'API EKS ; un agent sur les nœuds fournit les identifiantsLe cluster expose un fournisseur OIDC déclaré dans IAM ; le ServiceAccount porte l'annotation eks.amazonaws.com/role-arn
    Relation de confiance du rôleGénérique (pods.eks.amazonaws.com), le même rôle sert sur plusieurs clustersPropre à l'OIDC de chaque cluster : à modifier pour chaque nouveau cluster
    PrérequisAdd-on EKS Pod Identity AgentFournisseur OIDC IAM par cluster
    RecommandationChoix par défaut pour les nouveaux usagesToujours valable, notamment là où Pod Identity n'est pas disponible
     
    # Pod Identity : associer le ServiceAccount "orders" au rôle IAM de l'application
aws eks create-pod-identity-association \
  --cluster-name prod \
  --namespace boutique \
  --service-account orders \
  --role-arn arn:aws:iam::123456789012:role/orders-app

    Dans les deux cas, les SDK AWS récupèrent automatiquement des identifiants temporaires : aucune clé d'accès dans le code ni dans les Secrets.

    Points clés

    • Accès au cluster : access entries (API EKS) plutôt que le ConfigMap aws-auth.
    • Droits AWS des pods : Pod Identity (recommandé) ou IRSA, jamais le rôle du nœud.
    • Identifiants temporaires, moindre privilège, un rôle par application.

    Stockage et add-ons

    Les options de stockage

    ServiceDriver CSIMode d'accèsUsage
    Amazon EBSEBS CSI driverReadWriteOnceDisque d'une base de données, d'un StatefulSet
    Amazon EFSEFS CSI driverReadWriteManyFichiers partagés entre pods sur plusieurs nœuds et zones ; compatible Fargate
    Amazon FSxDrivers FSx (Lustre, NetApp ONTAP, OpenZFS)Selon le produitCalcul haute performance, besoins NAS spécifiques
    Amazon S3Mountpoint for Amazon S3 CSI driverAccès fichier à des objetsLecture de gros jeux de données (IA, analytique)
    Un volume EBS est lié à une zone de disponibilité Un disque EBS créé en zone a ne peut être monté que par un nœud de la zone a. Si le pod est replanifié dans une autre zone, il reste Pending. Utilisez volumeBindingMode: WaitForFirstConsumer dans la StorageClass, et assurez-vous qu'il y a toujours de la capacité de nœuds dans chaque zone utilisée. 
    apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: gp3
provisioner: ebs.csi.aws.com
parameters:
  type: gp3
  encrypted: "true"
volumeBindingMode: WaitForFirstConsumer
reclaimPolicy: Retain
allowVolumeExpansion: true

    Les add-ons EKS

    Un cluster a besoin de composants pour fonctionner : réseau, DNS, kube-proxy, drivers de stockage… EKS les propose sous forme d'add-ons managés, installés et mis à jour via l'API EKS, avec des versions validées pour chaque version de Kubernetes :

    • Amazon VPC CNI, CoreDNS, kube-proxy : le socle ;
    • Amazon EBS CSI Driver, Amazon EFS CSI Driver ;
    • EKS Pod Identity Agent ;
    • d'autres add-ons AWS ou de partenaires, comme l'agent CloudWatch, l'ADOT (distribution AWS d'OpenTelemetry) ou GuardDuty.
    Add-on managé ou installation Helm ? L'add-on managé simplifie les mises à jour et garantit la compatibilité de version. Certains composants importants ne sont pas des add-ons EKS et s'installent généralement avec Helm, par exemple l'AWS Load Balancer Controller ou Karpenter (sauf avec Auto Mode, qui les intègre). Dans tous les cas, gérez-les par le code (Terraform, GitOps).

    Points clés

    • EBS = RWO et lié à une AZ ; EFS = RWX multi-AZ.
    • StorageClass avec WaitForFirstConsumer, chiffrement et Retain pour les données critiques.
    • Add-ons managés pour le socle (CNI, CoreDNS, kube-proxy, CSI, Pod Identity Agent).
    Module 6

    Exploitation : mises à jour, observabilité et sécurité

    Mettre à jour un cluster

    1. Préparer : lire les notes de version ; vérifier les API dépréciées encore utilisées par vos manifestes et charts avec les EKS upgrade insights (ou des outils comme pluto et kubent) ; vérifier la compatibilité des add-ons et des outils (contrôleurs, opérateurs).
    2. Plan de contrôle : mise à jour d'une seule version mineure à la fois (1.32 → 1.33, pas 1.32 → 1.34). Une fois mis à jour, il ne peut pas revenir en arrière.
    3. Add-ons : passer aux versions compatibles.
    4. Nœuds : remplacer les nœuds par des nœuds à jour (groupes managés, Karpenter avec la dérive des AMI, ou automatiquement avec Auto Mode). Les PDB encadrent l'opération.
    Décalage de versions autorisé Les kubelets des nœuds peuvent avoir jusqu'à trois versions mineures de retard sur le plan de contrôle, mais jamais d'avance. Ne laissez cependant pas l'écart grandir : il rend chaque mise à jour plus risquée.

    Bonne pratique : tester d'abord la mise à jour sur un cluster de recette, et automatiser l'ensemble par le code. Certaines équipes préfèrent même créer un nouveau cluster et y basculer le trafic (blue/green de clusters).

    Observabilité

    • Journaux du plan de contrôle (API, audit, authentificateur, controller manager, scheduler) : désactivés par défaut. Activez au moins audit et authenticator, envoyés vers CloudWatch Logs.
    • CloudWatch Container Insights : métriques et logs des conteneurs, nœuds et pods.
    • Amazon Managed Service for Prometheus et Amazon Managed Grafana pour un écosystème Prometheus sans serveur à gérer.
    • Les plateformes tierces s'intègrent via un opérateur : par exemple le Dynatrace Operator, qui déploie OneAgent et ActiveGate sur le cluster (voir la formation Observabilité & Dynatrace).

    Sécurité

    • Endpoint de l'API privé, ou public restreint à des plages d'IP connues.
    • Chiffrement des Secrets avec AWS KMS (chiffrement d'enveloppe des données de l'API Kubernetes), avec une clé gérée par vous si votre politique l'impose.
    • Nœuds : AMI optimisées EKS récentes (Amazon Linux 2023, Bottlerocket), pas d'accès SSH ouvert (préférez SSM Session Manager), IMDSv2 obligatoire avec une limite de saut à 1 pour que les pods ne puissent pas récupérer le rôle du nœud.
    • Images : Amazon ECR avec analyse de vulnérabilités.
    • Détection des menaces : Amazon GuardDuty (analyse des journaux d'audit EKS et surveillance à l'exécution).
    • Tout le module 5 de la partie 2 s'applique : RBAC, Pod Security Standards, NetworkPolicies.

    Points clés

    • Mise à jour : préparer (API dépréciées), plan de contrôle une version à la fois, add-ons, puis nœuds.
    • Activer les journaux d'audit du plan de contrôle ; Container Insights ou Prometheus managé.
    • Endpoint restreint, KMS, IMDSv2, AMI à jour, GuardDuty.
    Module 7

    Infrastructure as Code et bonnes pratiques

    Créer et gérer un cluster par le code

    OutilUsage
    eksctlCLI officielle, très rapide pour créer un cluster de test ; configuration YAML possible
    Terraform / OpenTofuLe plus répandu en entreprise, avec le module communautaire terraform-aws-modules/eks/aws ; s'intègre au reste de l'infrastructure (VPC, IAM, RDS…)
    AWS CDK / CloudFormationPour les équipes déjà outillées sur ces technologies
    GitOps (Argo CD, Flux)Tout ce qui tourne dans le cluster : add-ons non managés, outils, applications
     
    module "eks" {
  source  = "terraform-aws-modules/eks/aws"
  version = "~> 21.0"

  name               = "prod"
  kubernetes_version = "1.33"
  vpc_id             = module.vpc.vpc_id
  subnet_ids         = module.vpc.private_subnets

  endpoint_public_access = false
  enable_cluster_creator_admin_permissions = true

  eks_managed_node_groups = {
    system = {
      instance_types = ["m7g.large"]
      min_size       = 2
      max_size       = 4
      desired_size   = 2
    }
  }
}

    Les noms des paramètres changent d'une version majeure du module à l'autre : référez-vous à la documentation de la version utilisée.

    Une répartition fréquente : Terraform crée le VPC, le cluster, les groupes de nœuds système, les rôles IAM et les associations Pod Identity, puis installe Argo CD, qui déploie tout le reste depuis Git.

    Check-list d'un cluster EKS de production

    🌐 Réseau

    VPC sur 3 AZ, sous-réseaux privés larges pour les pods, prefix delegation si besoin, endpoint API restreint, AWS Load Balancer Controller.

    🖥️ Calcul

    Petit groupe de nœuds managés pour les composants système, Karpenter (ou Auto Mode) pour les applications, Spot et Graviton où c'est possible.

    🔐 Identité

    Access entries avec des rôles SSO, Pod Identity par application, aucun droit applicatif sur le rôle des nœuds.

    🛡️ Sécurité

    Secrets chiffrés par KMS, Pod Security Standards, NetworkPolicies, IMDSv2, GuardDuty, images scannées.

    📈 Exploitation

    Journaux d'audit activés, supervision et alertes, PDB, mises à jour planifiées au rythme des versions.

    💰 Coûts

    Requests mesurées, consolidation, étiquettes de coût, suivi par namespace (Kubecost, AWS Split Cost Allocation Data).

    Pièges courants sur EKS
    • Sous-réseaux trop petits : épuisement des IP et pods bloqués.
    • Permissions AWS ajoutées au rôle des nœuds au lieu de Pod Identity ou IRSA.
    • Versions jamais mises à jour : passage coûteux en support étendu, puis mise à jour forcée.
    • Volumes EBS dans une zone sans capacité de nœuds : pods Pending.
    • Un load balancer par service, au lieu de mutualiser les ALB.
    • Un cluster créé à la main dans la console, impossible à reproduire.
