    Module 1

    Smartscape en profondeur : le modèle d'entités

    Dans la partie 1, Smartscape a été présenté comme la carte de topologie en temps réel. Cette carte repose sur un modèle d'entités : chaque composant surveillé est une entité typée, avec un identifiant, des propriétés et des relations avec d'autres entités. C'est ce modèle qui permet à Davis de remonter une chaîne de causes, et à vous de filtrer, regrouper et attribuer les données.

    Les principaux types d'entités

    CoucheType d'entitéIdentifiant / type DQL
    Expérience utilisateurApplication web, application mobile, moniteur synthétiquedt.entity.application, dt.entity.mobile_application, dt.entity.synthetic_test, dt.entity.http_check
    ServicesService (API web, base de données, file de messages…)dt.entity.service
    ProcessusGroupe de processus (ensemble logique), instance de processus (sur un hôte)dt.entity.process_group, dt.entity.process_group_instance
    InfrastructureHôte, disque, interface réseaudt.entity.host, dt.entity.disk…
    Conteneurs et cloudCluster et namespace Kubernetes, workload, pod ; ressources clouddt.entity.kubernetes_cluster, dt.entity.cloud_application…

    Chaque entité possède un identifiant unique stable (par exemple SERVICE-1A2B3C4D5E6F7A8B), un nom affiché, des propriétés (technologie, version, système d'exploitation…) et des tags.

    Groupe de processus et instance de processus

    C'est la notion la plus souvent mal comprise. Un groupe de processus (process group) rassemble les processus qui font le même travail, sur un ou plusieurs hôtes : par exemple les 6 instances Tomcat de l'application « commandes ». Chaque processus réel est une instance de groupe de processus (process group instance, PGI).

    Les services sont détectés à partir des groupes de processus. Si OneAgent regroupe mal les processus (deux applications différentes dans le même groupe, ou une même application éclatée en plusieurs groupes), les services, les problèmes et les tableaux de bord en héritent. On corrige ce regroupement avec des règles de détection des groupes de processus, souvent à partir de variables d'environnement comme DT_CLUSTER_ID ou les métadonnées Kubernetes.

    Les relations

    DirectionRelationExemple
    Verticale (pile technique)runs_on / runs, instance_of, belongs_to, containsLe service checkout tourne sur le groupe de processus checkout-jvm, dont les instances tournent sur les hôtes web-01 et web-02
    Horizontale (appels)calls / called_byLe service frontend appelle checkout, qui appelle payment et la base orders-db

    Les relations horizontales sont découvertes à partir des traces PurePath réellement observées : si deux services ne se sont jamais appelés pendant la période, ils n'apparaissent pas reliés. Les relations verticales viennent de ce que OneAgent voit sur l'hôte (processus, conteneurs, ports).

    Comment Davis s'en sert

    1. Davis détecte une anomalie sur le service frontend (hausse du temps de réponse).
    2. Il suit les relations calls vers les services appelés et constate que payment est aussi anormal.
    3. Il descend la pile verticale de payment : groupe de processus, instances, hôtes, et y trouve une saturation CPU sur un hôte.
    4. Il regroupe le tout dans un seul problème, avec l'hôte en cause racine et frontend parmi les impacts.
    Les angles morts de la topologie Davis ne peut relier que ce qu'il voit. Un composant non instrumenté (base de données sans OneAgent, appel vers un service externe, file de messages non prise en charge) apparaît au mieux comme une boîte noire. Pour une analyse causale fiable, visez une couverture OneAgent complète sur les chemins critiques, et complétez avec OpenTelemetry là où OneAgent n'est pas possible.

    Points clés

    • Smartscape repose sur des entités typées, avec un identifiant stable, des propriétés, des tags et des relations.
    • Groupe de processus = processus qui font le même travail ; instance = un processus réel.
    • Relations verticales (runs_on, belongs_to…) et horizontales (calls / called_by).
    • La qualité de la topologie conditionne la qualité de l'analyse causale de Davis.
    Module 2

    Smartscape : organiser et interroger la topologie

    Nommer et regrouper

    • Host groups : un paramètre passé à OneAgent à l'installation (--set-host-group=prod-web) qui regroupe les hôtes. Il influence la détection des groupes de processus : deux hôtes de host groups différents n'ont jamais leurs processus dans le même groupe. C'est le moyen le plus simple de séparer prod et recette sur une même technologie.
    • Règles de nommage : pour obtenir des noms lisibles (checkout [prod]) à partir de propriétés détectées.
    • Règles de détection des services : pour fusionner ou séparer des services (par exemple séparer les points d'entrée d'une même application selon l'URL).

    Le tagging

    Les tags servent partout : filtres, droits d'accès, profils d'alerte, coûts, dashboards. Trois façons de les poser :

    MéthodePrincipeRecommandation
    Tags importésRepris automatiquement des tags cloud (AWS, Azure), des labels et annotations Kubernetes, ou de variables d'environnement (DT_TAGS)À privilégier : la source de vérité reste au plus près de l'infrastructure
    Règles d'auto-taggingRègles qui posent un tag selon des conditions (nom, technologie, host group…) et le propagent dans la topologie (de l'hôte vers ses processus et services, par exemple)Très utile pour couvrir des couches entières de manière cohérente
    Tags manuelsAjoutés à la main dans l'interfaceÀ éviter : non reproductibles et vite oubliés
    Une convention de tags minimale environment (prod, recette, dev), application, owner (équipe responsable), criticality. Définissez-la une fois pour toutes et faites-la respecter dans vos pipelines de déploiement et vos modules Terraform.

    Interroger les entités en DQL

    Les entités sont accessibles dans Grail comme n'importe quelle autre donnée :

    // Lister les hôtes Linux avec leur nom et leur host group
fetch dt.entity.host
| filter osType == "LINUX"
| fields id, entity.name, hostGroupName

// Enrichir des logs avec le nom lisible de l'hôte
fetch logs
| filter loglevel == "ERROR"
| fieldsAdd host = entityName(dt.entity.host)
| summarize erreurs = count(), by: { host }

// Réutiliser un sélecteur d'entités « classique » (tags, types…)
fetch logs
| filter in(dt.entity.host, classicEntitySelector("type(HOST),tag(environment:prod)"))

    Les relations sont aussi interrogeables (par exemple les services appelés par un service donné). La syntaxe dédiée évolue avec le nouveau Smartscape stocké dans Grail : consultez la documentation DQL de votre environnement pour la forme exacte.

    Étendre la topologie

    Pour des composants que OneAgent ne voit pas (équipements réseau, applications métier, appareils IoT), on peut définir une topologie personnalisée (generic topology) : des règles créent des entités et des relations à partir des métriques, logs ou événements ingérés. Ces entités se comportent ensuite comme les autres : tags, problèmes, dashboards.

    Points clés

    • Host groups, règles de nommage et de détection pour une topologie propre.
    • Tags importés et auto-tagging plutôt que tags manuels ; une convention minimale partagée.
    • Entités interrogeables en DQL (fetch dt.entity.*, entityName(), classicEntitySelector()).
    • La topologie personnalisée intègre des composants non instrumentés.
    Module 3

    DQL avancé

    La partie 1 a présenté les commandes de base (fetch, filter, summarize, sort, limit). Voici les techniques qui permettent de répondre à des questions plus riches.

    Délimiter les données lues

    fetch logs, from: now() - 24h, to: now() - 1h, scanLimitGBytes: 50
| filter k8s.namespace.name == "boutique"

    Avec Grail, les requêtes sont facturées selon le volume de données lues. Limiter la période, filtrer tôt (juste après fetch) et éviter les contains() sur de gros volumes rend les requêtes plus rapides et moins coûteuses. samplingRatio lit un échantillon des données pour une estimation rapide.

    Extraire des champs : parse et DPL

    parse extrait des champs structurés d'un texte avec le DPL (Dynatrace Pattern Language) :

    // Ligne : "Payment refused order=8812 amount=129.90 reason=PSP_TIMEOUT"
fetch logs
| filter matchesPhrase(content, "Payment refused")
| parse content, "LD 'order=' INT:order ' amount=' DOUBLE:amount ' reason=' WORD:reason"
| summarize total = sum(amount), nb = count(), by: { reason }
    Parser à la requête ou à l'ingestion ? parse en DQL est idéal pour explorer. Pour un champ utilisé tous les jours (dashboards, alertes), faites l'extraction une fois pour toutes à l'ingestion avec OpenPipeline : les requêtes deviennent plus simples et plus rapides.

    Séries temporelles

    // À partir de métriques
timeseries p95 = percentile(dt.service.request.response_time, 95),
           by: { dt.entity.service }, interval: 5m

// À partir d'enregistrements (logs, spans, événements) : makeTimeseries
fetch logs
| filter loglevel == "ERROR"
| makeTimeseries erreurs = count(), by: { k8s.namespace.name }, interval: 10m

    Les noms exacts des métriques varient selon les versions : la liste se consulte dans le navigateur de métriques ou avec l'autocomplétion des Notebooks.

    Combiner des sources

    CommandeUsage
    lookupAjouter des champs venant d'une autre requête, par correspondance de clé (enrichissement)
    joinJointure entre deux jeux de données (inner, left outer…)
    appendAjouter à la suite les résultats d'une autre requête
    dedupNe garder qu'un enregistrement par valeur de clé
    expandTransformer un tableau en plusieurs enregistrements
    fieldsAdd / fieldsRemove / fieldsRenameCalculer, retirer, renommer des champs
     
    // Enrichir les erreurs de logs avec le propriétaire du service
fetch logs
| filter loglevel == "ERROR" and isNotNull(dt.entity.service)
| summarize erreurs = count(), by: { dt.entity.service }
| lookup [ fetch dt.entity.service | fields id, entity.name, tags ],
         sourceField: dt.entity.service, lookupField: id, prefix: "svc."
| sort erreurs desc

    Les données métier

    // Chiffre d'affaires par heure à partir des business events
fetch bizevents
| filter event.type == "com.acme.order.completed"
| makeTimeseries ca = sum(amount), interval: 1h

    Points clés

    • Coût et performance : période courte, filtres tôt, scanLimitGBytes.
    • parse + DPL pour explorer ; OpenPipeline pour les extractions permanentes.
    • timeseries pour les métriques, makeTimeseries pour les enregistrements.
    • lookup, join, append pour combiner les sources.
    Module 4

    Les Notebooks : explorer et tester

    Un Notebook Dynatrace est un document interactif, comparable à un notebook Jupyter, qui mélange requêtes DQL, visualisations, texte et code. C'est l'espace de travail idéal pour explorer les données de Grail et mettre au point des requêtes avant de les utiliser ailleurs.

    Les types de sections

    🔎 Requête DQL

    Une requête, son résultat (tableau, graphique…) et sa période. Chaque section s'exécute indépendamment.

    📝 Markdown

    Texte, titres, liens : pour expliquer une analyse ou documenter une procédure.

    💻 Code

    Du JavaScript exécuté dans la plateforme : appeler des API Dynatrace ou externes, transformer des données.

    📊 Données de l'interface

    Des sections préconfigurées pour explorer logs, métriques ou événements sans écrire de DQL.

    Mettre au point une requête : la démarche

    1. Partir petit : une période courte (15 minutes ou 1 heure) et un limit 20 pour voir la forme des données et le nom exact des champs.
    2. Ajouter les filtres un par un, en vérifiant à chaque étape que le résultat reste cohérent.
    3. Agréger et visualiser : summarize ou makeTimeseries, puis choisir la visualisation.
    4. Vérifier le coût : le volume scanné s'affiche après l'exécution. Si une requête lit des centaines de Go, resserrez la période ou les filtres.
    5. Élargir la période à celle voulue pour l'usage final.
    6. Réutiliser : copier la requête dans une tuile de dashboard, une tâche de workflow, un objectif SLO ou une alerte.
    Astuce Gardez un Notebook « bac à sable » par équipe avec vos requêtes de référence commentées : il devient une documentation vivante de la façon d'interroger vos données. L'assistant d'IA générative (Davis CoPilot) peut aussi proposer une requête DQL à partir d'une question en langage naturel, à vérifier avant usage.

    Usages typiques

    • Investigation d'un incident : rassembler dans un même document les requêtes, graphiques et constats, puis le partager avec l'équipe.
    • Prototypage de dashboards et d'alertes.
    • Tests de pipeline : vérifier qu'une règle OpenPipeline produit bien les champs attendus, ou qu'un nouveau flux de logs arrive.
    • Analyses ponctuelles : capacité, coûts d'ingestion par source, tendances sur plusieurs semaines.

    Partage et droits

    Un Notebook est privé par défaut. On peut le partager avec des utilisateurs ou des groupes, en lecture ou en écriture. Les personnes qui l'ouvrent ne voient que les données auxquelles leurs propres droits donnent accès (voir la partie 4) : partager un Notebook ne donne pas accès à des données supplémentaires.

    Points clés

    • Notebook = requêtes DQL, visualisations, Markdown et code dans un même document.
    • Démarche : partir petit, filtrer, agréger, vérifier le volume scanné, puis élargir.
    • Usages : investigation, prototypage, tests de pipelines, analyses ponctuelles.
    • Le partage respecte les droits d'accès aux données de chacun.
    Module 5

    Créer des dashboards

    Les éléments d'un dashboard

    ÉlémentRôle
    Tuile de donnéesUne requête DQL et sa visualisation
    Tuile MarkdownTitres, explications, liens vers les runbooks
    Tuile de codeDonnées calculées en JavaScript (appel d'API, calcul personnalisé)
    VariablesListes déroulantes en haut du dashboard (environnement, namespace, service…) réutilisées dans les requêtes
    Période et segmentsLa période globale et les filtres appliqués à toutes les tuiles

    Choisir la visualisation

    QuestionVisualisation
    Quelle est la valeur actuelle d'un indicateur ?Valeur unique (single value), avec seuils de couleur
    Comment évolue-t-il dans le temps ?Courbe ou aire
    Comment se comparent plusieurs éléments ?Barres, triées
    Quel est l'état d'un grand nombre d'éléments ?Honeycomb (alvéoles colorées)
    Quel est le détail ?Tableau ou liste d'enregistrements
    Quelle est la répartition d'une distribution ?Heatmap ou histogramme

    Évitez les camemberts pour plus de quatre ou cinq catégories : les barres triées se lisent beaucoup mieux.

    Les variables

    Une variable peut être une liste fixe ou le résultat d'une requête. Elle s'utilise ensuite dans les requêtes des tuiles avec le préfixe $ :

    // Variable "Namespace", alimentée par une requête
fetch dt.entity.cloud_application_namespace
| fields entity.name
| sort entity.name

// Tuile qui utilise la variable
fetch logs
| filter k8s.namespace.name == $Namespace and loglevel == "ERROR"
| makeTimeseries erreurs = count(), interval: 5m

    Un seul dashboard paramétrable remplace ainsi une dizaine de dashboards copiés-collés, un par namespace ou par application.

    Concevoir un bon dashboard

    1. Un public, une question : un dashboard d'astreinte (« tout va-t-il bien ? ») n'est pas un dashboard de direction (« quel impact métier ? ») ni un dashboard d'analyse de capacité.
    2. Du général au détail : indicateurs clés et état des SLO en haut, tendances au milieu, détail en bas.
    3. Des seuils explicites : vert, orange, rouge, cohérents avec vos SLO et alertes.
    4. Des liens vers les Notebooks d'investigation, les runbooks et les problèmes Davis.
    5. Peu de tuiles : au-delà d'une quinzaine, le dashboard n'est plus lu.

    Performance et coût

    • Chaque tuile exécute sa requête à l'ouverture et à chaque rafraîchissement : un dashboard de 20 tuiles affiché en continu sur un écran avec un rafraîchissement d'une minute lit beaucoup de données.
    • Préférez les métriques (timeseries), y compris celles extraites des logs par OpenPipeline, aux agrégations de logs bruts sur de longues périodes.
    • Réglez un intervalle de rafraîchissement adapté à l'usage.

    Partage et gestion

    Comme les Notebooks, les dashboards sont privés par défaut et se partagent avec des utilisateurs ou des groupes. Dynatrace fournit aussi des dashboards prêts à l'emploi (Kubernetes, hôtes, AWS…), utiles comme point de départ. Les dashboards se versionnent et se déploient par le code, avec Terraform ou Monaco (voir la partie 4).

    Dashboards classiques Les environnements plus anciens contiennent des dashboards « classiques », construits avec d'autres tuiles et un autre langage de sélection de métriques. Ils coexistent avec la nouvelle application Dashboards, basée sur DQL, vers laquelle il est recommandé de migrer progressivement.

    Points clés

    • Tuiles DQL, Markdown et code ; variables $Nom pour un dashboard paramétrable.
    • Visualisation choisie selon la question ; seuils cohérents avec les SLO.
    • Un public et une question par dashboard ; peu de tuiles, du général au détail.
    • Surveillez le volume scanné ; préférez les métriques ; versionnez par le code.
