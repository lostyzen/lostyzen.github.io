    Dynatrace : la surveillance synthétique

    Cette troisième partie est consacrée à la surveillance synthétique (Synthetic Monitoring) : simuler des utilisateurs et des appels pour vérifier en continu la disponibilité et la performance de vos applications, API et équipements, même quand personne ne les utilise. Elle se termine par un quiz de validation.

    Module 1

    Les principes de la surveillance synthétique

    Un moniteur synthétique exécute un test à intervalles réguliers depuis un ou plusieurs emplacements : appeler une API, charger une page, dérouler un parcours de connexion, joindre un équipement réseau. Chaque exécution mesure la disponibilité (le test a-t-il réussi ?) et la performance (en combien de temps ?).

    Pourquoi le synthétique ?

    🌙 Détection proactive

    Une panne à 3 h du matin est détectée avant l'arrivée des premiers utilisateurs, même sans aucun trafic.

    📏 Référence stable

    Mêmes conditions à chaque exécution : idéal pour comparer les performances dans le temps et entre versions.

    🌍 Vue géographique

    Vérifier l'accès depuis différents pays ou sites de l'entreprise.

    🤝 Engagements contractuels

    Mesurer objectivement la disponibilité d'un service pour un SLA ou un SLO.

    🧪 Avant la mise en production

    Tester un environnement de recette ou une nouvelle version avant l'ouverture aux utilisateurs.

    🔌 Dépendances tierces

    Surveiller les API de partenaires (paiement, transport) dont vous dépendez.

    Synthétique et RUM

    SynthétiqueRUM
    SourceRobots, parcours définis à l'avanceUtilisateurs réels
    Disponibilité des mesuresEn continu, 24 h/24Seulement quand il y a du trafic
    ConditionsContrôlées et constantesToute la diversité réelle (navigateurs, réseaux, appareils)
    Répond à« Le service fonctionne-t-il ? »« Comment les utilisateurs le vivent-ils ? »

    Les deux se complètent : le synthétique alerte tôt et sert de référence, le RUM mesure l'expérience réelle. Pour aller plus loin sur le RUM, voir l'article Le Real User Monitoring (RUM) dans Dynatrace et l'injection du tag JavaScript.

    Les types de moniteurs

    TypeCe qu'il faitUsage
    Moniteur HTTPEnvoie une ou plusieurs requêtes HTTP et vérifie les réponses, sans navigateurAPI, points de santé, services web ; léger et peu coûteux

    Points clés

    • Moniteur = test exécuté régulièrement depuis des emplacements ; mesure disponibilité et performance.
    • Détection proactive, référence stable, vue géographique, mesure des engagements.
    • Complémentaire du RUM.
    • Types : HTTP, navigateur (URL unique ou parcours), disponibilité réseau.
    Module 2

    Les moniteurs HTTP

    Un moniteur HTTP n'utilise pas de navigateur : il envoie des requêtes et analyse les réponses. Il est rapide, économique et idéal pour les API et les points de santé.

    Configurer une requête

    • URL et méthode (GET, POST, PUT…), en-têtes et corps de la requête ;
    • Authentification : basique, jeton, certificat client, OAuth… avec des identifiants issus du coffre-fort d'identifiants (credential vault) ;
    • Règles de validation : code de statut attendu, présence ou absence d'un texte ou d'une expression régulière dans la réponse ;
    • Seuils de performance : durée au-delà de laquelle le test est considéré comme lent ;
    • Validation du certificat TLS et alerte avant son expiration.
    Un code 200 ne suffit pas Une API peut répondre 200 avec un message d'erreur dans le corps, ou une page de maintenance. Ajoutez toujours une règle de validation sur le contenu : par exemple, vérifier que la réponse contient "status":"UP".

    Les moniteurs multi-requêtes

    Un moniteur HTTP peut enchaîner plusieurs requêtes pour tester un scénario d'API complet : obtenir un jeton, créer une ressource, la relire, la supprimer. Des scripts JavaScript exécutés avant ou après chaque requête permettent de :

    • extraire une valeur d'une réponse (un jeton, un identifiant) pour la réutiliser dans la requête suivante ;
    • construire dynamiquement une requête (horodatage, signature) ;
    • faire échouer le test selon une logique métier plus fine que les règles de validation.
    // Script après la requête "Obtenir un jeton" (illustratif)
var body = JSON.parse(response.getResponseBody());
if (!body.access_token) {
  api.fail("Aucun jeton dans la réponse");
}
api.setValue("token", body.access_token);   // réutilisé ensuite via {token}

    Les noms exacts des objets et méthodes disponibles dans les scripts sont décrits dans la documentation Dynatrace des moniteurs HTTP.

    Bonnes pratiques

    • Tester un point de santé applicatif qui vérifie réellement les dépendances essentielles, plutôt qu'une simple page statique.
    • Pour les scénarios qui écrivent des données, utiliser un compte de test et nettoyer en fin de scénario.
    • Ne jamais mettre de mot de passe ou de jeton en clair dans le moniteur : passer par le coffre-fort d'identifiants.

    Points clés

    • Moniteur HTTP : sans navigateur, rapide et économique, idéal pour les API.
    • Toujours valider le contenu de la réponse, pas seulement le code de statut.
    • Multi-requêtes et scripts pour enchaîner des appels et réutiliser des valeurs.
    • Identifiants dans le coffre-fort, comptes de test, nettoyage.
    Module 3

    Les moniteurs navigateur

    Un moniteur navigateur exécute un vrai navigateur Chrome : le JavaScript s'exécute, les ressources se chargent, les pages s'affichent. Il mesure donc ce qu'un utilisateur verrait, y compris les Core Web Vitals, les erreurs JavaScript et les ressources tierces lentes.

    Enregistrer un parcours

    Les parcours (clickpaths) s'enregistrent avec le Dynatrace Synthetic Recorder, une extension pour Chrome : on navigue normalement sur le site, et chaque action (clic, saisie, sélection, navigation) devient un événement du moniteur. On peut ensuite modifier le script, dans l'éditeur visuel ou en mode script (JSON).

    1. Démarrer l'enregistrement depuis l'assistant de création de moniteur.
    2. Dérouler le parcours : page d'accueil → connexion → recherche → fiche produit.
    3. Vérifier et rendre les localisateurs robustes (voir ci-dessous).
    4. Ajouter des validations : tel texte ou tel élément doit être présent à telle étape.
    5. Remplacer les mots de passe saisis par des identifiants du coffre-fort.
    6. Lancer une exécution de test, puis activer le moniteur.

    Des parcours robustes

    La cause n° 1 des fausses alertes est un parcours qui casse dès que la page change un peu. Pour l'éviter :

    • Localisateurs stables : préférez un identifiant (#login-button) ou un attribut dédié aux tests ([data-testid="login"]) à un chemin CSS ou XPath long et fragile. Le Recorder enregistre plusieurs localisateurs de secours pour chaque élément.
    • Attendre les bons éléments : configurer l'attente d'un élément ou d'un texte précis plutôt qu'un délai fixe.
    • Valider chaque étape importante : sans validation, un parcours peut « réussir » sur une page d'erreur.
    • Collaborer avec les développeurs : ajouter des attributs data-testid stables profite aussi aux tests automatisés.
    • Gérer les bannières de consentement aux cookies et les fenêtres surgissantes au début du parcours.
    Attention aux effets de bord Un parcours exécuté toutes les 15 minutes depuis 4 emplacements tourne près de 400 fois par jour. S'il passe une vraie commande, envoie un vrai e-mail ou crée un vrai compte, les conséquences sont réelles. Utilisez des comptes et des données de test, arrêtez le parcours avant l'étape irréversible, ou prévoyez un environnement où ces actions sont neutralisées.

    Les résultats d'un moniteur navigateur

    • Disponibilité et durée totale, détail par événement du parcours ;
    • Cascade des ressources chargées (scripts, images, API) : idéal pour repérer un appel tiers lent ;
    • Capture d'écran de la page au moment d'un échec ;
    • Lien vers les traces côté serveur quand l'application est surveillée par OneAgent.

    Points clés

    • Moniteur navigateur = vrai Chrome : JavaScript, ressources, Web Vitals.
    • Parcours enregistrés avec le Synthetic Recorder, puis rendus robustes.
    • Localisateurs stables, attentes d'éléments, validations à chaque étape.
    • Jamais d'actions réelles irréversibles ; comptes et données de test.
    Module 4

    Emplacements publics, privés et disponibilité réseau

    Emplacements publics et privés

    Emplacements publicsEmplacements privés
    Hébergés parDynatrace, chez les grands fournisseurs cloud, dans de nombreuses régions du mondeVous, sur un ou plusieurs ActiveGates avec la fonction Synthetic activée, ou dans un cluster Kubernetes
    TestentCe qui est accessible depuis InternetLes applications internes (intranet, back-office, API privées) et l'accès depuis vos sites
    ExploitationAucuneDimensionnement, mises à jour, haute disponibilité (plusieurs ActiveGates par emplacement)
    Choisir les emplacements Pour un site public, prenez des emplacements proches de vos utilisateurs réels (par exemple Paris, Francfort et Londres pour une clientèle européenne) et au moins trois emplacements : cela permet de distinguer une vraie panne d'un problème réseau local (module 5). Pour une application interne, placez des emplacements privés dans les sites ou réseaux d'où se connectent les utilisateurs.

    Les moniteurs de disponibilité réseau

    Ces moniteurs testent l'accessibilité réseau de cibles, sans passer par HTTP :

    • ICMP : la cible répond-elle au ping, avec quelle latence et quelle perte de paquets ?
    • TCP : le port (base de données, serveur de messagerie, service propriétaire) accepte-t-il les connexions ?
    • DNS : le nom est-il résolu, et vers les bonnes adresses ?

    Ils s'exécutent depuis des emplacements privés et servent à surveiller des équipements et services internes : routeurs, imprimantes, serveurs sans OneAgent, accès à des partenaires par VPN. Un même moniteur peut tester de nombreuses cibles.

    Fréquence d'exécution

    Chaque moniteur s'exécute à une fréquence choisie, par exemple toutes les minutes pour une API critique, toutes les 15 minutes pour un parcours navigateur. Plus la fréquence est élevée, plus la détection est rapide… et plus le coût est élevé (module 6). Les fréquences proposées dépendent du type de moniteur.

    Points clés

    • Publics : gérés par Dynatrace, pour ce qui est exposé sur Internet.
    • Privés : ActiveGates (ou Kubernetes) chez vous, pour les applications internes.
    • Au moins trois emplacements pour distinguer une panne d'un incident local.
    • Moniteurs réseau ICMP, TCP, DNS depuis des emplacements privés.
    Module 5

    Alertes, détection des pannes et SLO

    Panne globale et panne locale

    Un test qui échoue une fois depuis un seul emplacement ne signifie pas forcément que le service est en panne : le problème peut venir du réseau de cet emplacement. Dynatrace distingue :

    • Panne globale (global outage) : le test échoue depuis tous les emplacements ;
    • Panne locale (local outage) : le test échoue depuis un nombre donné d'emplacements, pendant un nombre donné d'exécutions consécutives.

    On règle ces seuils pour chaque moniteur. L'option de nouvelle tentative en cas d'erreur relance immédiatement un test échoué avant de le compter comme un échec, ce qui élimine beaucoup de faux positifs dus à un incident réseau ponctuel.

    Les seuils de performance

    En plus de la disponibilité, on définit des seuils de durée, globaux ou par étape (par exemple « la page de résultats de recherche doit s'afficher en moins de 3 s »). Un dépassement répété ouvre un problème de lenteur.

    Des problèmes, pas seulement des alertes

    Les échecs synthétiques deviennent des problèmes Davis, comme les autres anomalies. Quand l'application testée est surveillée par OneAgent, Davis peut relier l'échec du moniteur à la cause racine côté serveur : service en erreur, base saturée, déploiement récent. Les notifications passent ensuite par les mêmes canaux que les autres problèmes, en général via un workflow (voir la partie 4).

    Fenêtres de maintenance

    Pendant une maintenance planifiée, un site volontairement indisponible ne doit ni réveiller l'astreinte ni dégrader le calcul de disponibilité. Déclarez des fenêtres de maintenance : selon leur configuration, elles suspendent l'exécution des moniteurs ou les alertes sur la période.

    SLO de disponibilité

    Les résultats synthétiques sont une excellente base pour un SLO de disponibilité : « le parcours de connexion doit réussir dans 99,9 % des exécutions sur 30 jours ». On peut aussi interroger les résultats en DQL, dans un Notebook ou un dashboard, pour suivre la disponibilité par emplacement ou par étape.

    Points clés

    • Panne globale (tous les emplacements) et panne locale (N emplacements, X fois de suite).
    • Nouvelle tentative en cas d'erreur pour limiter les faux positifs.
    • Échecs = problèmes Davis, reliés à la cause racine côté serveur si OneAgent est présent.
    • Fenêtres de maintenance et SLO de disponibilité.
    Module 6

    Coûts et bonnes pratiques

    Comprendre la consommation

    Le synthétique est facturé selon le nombre d'exécutions : nombre d'actions pour les moniteurs navigateur, nombre de requêtes pour les moniteurs HTTP, nombre de requêtes réseau pour la disponibilité réseau. La consommation se calcule simplement :

    Exemple de calcul
    Parcours navigateur de 5 actions, toutes les 15 minutes, depuis 3 emplacements :
    4 exécutions/heure × 24 h × 30 jours = 2 880 exécutions par emplacement et par mois.
    2 880 × 3 emplacements × 5 actions = 43 200 actions par mois.
    Le même parcours toutes les 5 minutes en consomme trois fois plus.

    Les moniteurs navigateur sont les plus coûteux, les moniteurs HTTP beaucoup moins. Les emplacements privés n'évitent pas la consommation de licence, mais ajoutent le coût de leurs ActiveGates.

    Une stratégie équilibrée

    CibleMoniteur conseilléFréquence indicative
    API et points de santé critiquesHTTP1 à 5 min
    Page d'accueil, disponibilité d'un siteHTTP (contenu validé), ou navigateur URL unique5 à 15 min
    Parcours métier critiques (connexion, achat)Parcours navigateur10 à 15 min
    Parcours secondairesParcours navigateur30 à 60 min
    Équipements et services internes non HTTPDisponibilité réseau1 à 5 min

    Check-list

    • Couvrir ce qui compte : quelques parcours critiques bien conçus valent mieux que des dizaines de moniteurs fragiles.
    • Nommer et taguer les moniteurs (application, environnement, équipe propriétaire) pour les retrouver et router les alertes.
    • Gérer par le code : les moniteurs se créent avec Terraform ou Monaco (ressources de type dynatrace_http_monitor, dynatrace_browser_monitor), ce qui permet de les dupliquer entre environnements.
    • Identifiants dans le coffre-fort, comptes de test dédiés, pas d'actions réelles irréversibles.
    • Revoir régulièrement les moniteurs : supprimer ceux dont personne ne regarde les résultats, ajuster ceux qui génèrent de fausses alertes.
    • Prévenir les équipes concernées : un pare-feu applicatif (WAF) ou une protection anti-robots peut bloquer les emplacements synthétiques ; il faut alors autoriser leurs adresses IP.
